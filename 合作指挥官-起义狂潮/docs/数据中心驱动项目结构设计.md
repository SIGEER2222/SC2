# 数据中心驱动项目结构设计

> 状态：设计定稿 v1
> 日期：2026-07-11
> 依据：`docs/银河编辑器/数据空间使用指南.md`
> 关联：`docs/指挥官地图组合框架设计.md`
> 实施跟踪：`docs/经验总结/` 下与数据中心相关的条目

## 1. 目标

当前项目正在从“单地图/单指挥官修补”转向“任意指挥官 × 任意地图”的组合平台。为了避免 Catalog、Galaxy、地图本地数据和适配层继续堆在一起，需要引入一个更清晰的数据中心结构。

这里的“数据中心”不是运行时新机制，而是基于 SC2 数据空间能力建立的项目组织方式：

```text
GameData.xml
  -> <Includes>
      -> DataSpace XML
      -> DataSpace XML
      -> DataSpace XML
```

目标是：

- 把可复用 Catalog 数据从地图本地文件中抽出来。
- 把指挥官数据、地图族补丁、通用能力、测试数据分开维护。
- 让 `CommanderPackage`、`MapAdapter`、`CapabilityPackage` 都能拥有自己的数据空间。
- 让未来的组合生成器可以按需拼装数据中心，而不是复制整包 XML。
- 保持地图本地数据只负责任务语义，减少与指挥官数据互相覆盖。

## 2. 核心判断

### 2.1 数据空间适合做项目结构，不适合替代依赖规则

数据空间本质是 Catalog XML 的组织和入口机制。它能让数据更清晰、更容易迁移，但不会改变 SC2 的依赖加载顺序：

```text
父依赖
  -> 后加载依赖
  -> 地图本地 GameData
  -> Galaxy 运行时修改
```

因此：

- 数据空间不能自动解决同 ID 覆盖。
- 数据空间不能替代 MapProfile 的依赖顺序。
- 数据空间不能替代 PairPatch。
- 数据空间可以让字段来源更清晰，降低冲突定位成本。

### 2.2 地图本地数据应该越来越薄

长期目标不是让每张地图保留大量 `UnitData.xml`、`AbilData.xml`、`ActorData.xml`，而是：

- 地图本地只保留任务专属数据。
- 指挥官单位、技能、按钮、Actor 放入 Commander 数据中心。
- 地图族共享补丁放入 MapFamily 数据中心。
- 通用机制放入 Capability 数据中心。
- 组合例外放入 PairPatch 数据空间或生成 patch。

## 3. 推荐目录结构

建议项目内逐步形成以下结构：

```text
合作指挥官-起义狂潮/
├─ Mods/
│  ├─ Platform/
│  │  ├─ PlatformKernel.SC2Mod/
│  │  └─ Capabilities/
│  │     ├─ HeroRevive.SC2Mod/
│  │     ├─ TopPanel.SC2Mod/
│  │     └─ RuntimeProbe.SC2Mod/
│  ├─ Commanders/
│  │  ├─ TerranRaynor.SC2Mod/
│  │  ├─ ZergAbathur.SC2Mod/
│  │  └─ ...
│  ├─ MapFamilies/
│  │  ├─ RebornHotS.SC2Mod/
│  │  └─ 7vs1.SC2Mod/
│  └─ Compatibility/
│     ├─ RebornHotS_TerranRaynor.SC2Mod/
│     └─ ...
├─ Shared/
│  ├─ Commanders/
│  ├─ Maps/
│  ├─ DataCenters/
│  └─ Compatibility/
└─ Maps/
   ├─ source/
   ├─ generated/
   └─ smoke/
```

说明：

- `Mods/Platform` 放运行时内核和通用能力。
- `Mods/Commanders` 放可选择的指挥官数据中心。
- `Mods/MapFamilies` 放地图族适配和共享补丁，例如 Reborn。
- `Mods/Compatibility` 放少数必须独立承载的组合 patch。
- `Shared/DataCenters` 放机器可读清单和来源说明，不直接替代 SC2 Mod。
- `Maps/generated` 放由组合生成器输出的地图工作副本。

## 4. 数据中心内部结构

每个数据中心 Mod 使用一致结构：

```text
Example.SC2Mod/
├─ ComponentList.SC2Components
├─ DocumentInfo
└─ Base.SC2Data/
   ├─ GameData.xml
   └─ GameData/
      ├─ Units.xml
      ├─ Abilities.xml
      ├─ Buttons.xml
      ├─ Actors.xml
      ├─ Effects.xml
      ├─ Behaviors.xml
      ├─ Upgrades.xml
      └─ Requirements.xml
```

`Base.SC2Data/GameData.xml`：

```xml
<?xml version="1.0" encoding="utf-8"?>
<Includes>
    <Catalog path="GameData/Units.xml"/>
    <Catalog path="GameData/Abilities.xml"/>
    <Catalog path="GameData/Buttons.xml"/>
    <Catalog path="GameData/Actors.xml"/>
    <Catalog path="GameData/Effects.xml"/>
    <Catalog path="GameData/Behaviors.xml"/>
    <Catalog path="GameData/Upgrades.xml"/>
    <Catalog path="GameData/Requirements.xml"/>
</Includes>
```

规则：

- 文件名使用 ASCII。
- XML 内容统一 UTF-8。
- 一个数据空间文件只服务一个清晰主题。
- 不使用 `Unit.xml`、`Actor.xml` 这类过于通用的文件名。
- 跨中心复用时，优先迁移整个数据空间，而不是手工复制散碎节点。

## 5. 数据中心分类

### 5.1 PlatformDataCenter

用于通用运行时和工具数据。

放入：

- 通用 dummy unit。
- 通用 validator unit。
- 通用 behavior marker。
- 通用 top panel caster 基类。
- 通用 runtime probe 数据。

不放入：

- 具体指挥官单位。
- 具体地图任务单位。
- 具体地图胜负逻辑。

### 5.2 CapabilityDataCenter

用于可复用能力模块。

示例：

```text
HeroRevive.SC2Mod/
  GameData/HeroReviveUnits.xml
  GameData/HeroReviveBehaviors.xml
  GameData/HeroReviveEffects.xml

TopPanel.SC2Mod/
  GameData/TopPanelAbilities.xml
  GameData/TopPanelButtons.xml
  GameData/TopPanelActors.xml
```

原则：

- 只定义机制，不定义某个指挥官的具体内容。
- 通过 CommanderPackage 的元数据绑定到具体单位和行为。
- 能被多个指挥官依赖。

### 5.3 CommanderDataCenter

每个指挥官一个数据中心。

建议结构：

```text
TerranRaynor.SC2Mod/
└─ Base.SC2Data/
   ├─ GameData.xml
   └─ GameData/
      ├─ RaynorUnits.xml
      ├─ RaynorBuildings.xml
      ├─ RaynorAbilities.xml
      ├─ RaynorButtons.xml
      ├─ RaynorActors.xml
      ├─ RaynorEffects.xml
      ├─ RaynorBehaviors.xml
      ├─ RaynorUpgrades.xml
      └─ RaynorRequirements.xml
```

所有 canonical 指挥官数据归这里。

不得：

- 把地图点、区域、任务触发器写入指挥官中心。
- 写入 Reborn、7vs1、XM 专属逻辑。
- 依赖某个地图族适配器。

### 5.4 MapFamilyDataCenter

地图族共享数据中心。

Reborn 示例：

```text
RebornHotS.SC2Mod/
└─ Base.SC2Data/
   ├─ GameData.xml
   └─ GameData/
      ├─ RebornBridgeUnits.xml
      ├─ RebornBridgeAbilities.xml
      ├─ RebornBridgeButtons.xml
      ├─ RebornBridgeRequirements.xml
      └─ RebornBridgeActors.xml
```

用途：

- 地图族共享的缺失按钮。
- 地图族共享的 Requirement 修正。
- 地图族共享的 actor/模型引用补全。
- 地图族适配器所需的桥接单位或行为。

不得：

- 放入某个指挥官的 canonical 单位。
- 覆盖地图任务目标或剧情。
- 读写剧情 Bank。

### 5.5 PairPatchDataCenter

少量特定组合例外。

命名：

```text
Compatibility/RebornHotS_TerranRaynor.SC2Mod
Compatibility/RebornHotS_Karax.SC2Mod
```

只允许放：

- 某地图族与某指挥官组合必需的字段修正。
- 无法放入公共 MapFamily 或 Commander 的冲突修复。
- 可删除、可验证的临时桥接数据。

每个 PairPatch 必须配套 manifest：

```json
{
  "schemaVersion": 1,
  "mapFamily": "RebornHotS",
  "commander": "TerranRaynor",
  "reason": "map-local override removes required command card entry",
  "catalogPatches": [],
  "validation": []
}
```

## 6. 与 CompositionPlan 的关系

CompositionPlan 不直接操作散碎 XML，而是组合数据中心：

```text
MapProfile
  -> 原地图依赖
  -> PlatformDataCenter
  -> CapabilityDataCenter
  -> CommanderDataCenter
  -> MapFamilyDataCenter
  -> PairPatchDataCenter
  -> 地图本地 patch
```

依赖层建议：

| 层级 | 内容 | 说明 |
| --- | --- | --- |
| L0 | 官方 Campaign / 官方 Mod | Liberty、Void、SwarmStory、StarCoop |
| L1 | 原地图依赖 | 保留原图声明 |
| L2 | PlatformDataCenter | 通用运行时数据 |
| L3 | CapabilityDataCenter | HeroRevive、TopPanel 等 |
| L4 | CommanderDataCenter | 当前选中的指挥官 |
| L5 | MapFamilyDataCenter | Reborn、7vs1、XM 地图族适配 |
| L6 | PairPatchDataCenter | 特定组合例外 |
| L7 | 地图本地 patch | 最后覆盖，只放必要字段 |

这样可以避免当前项目中常见的问题：

- 一个包里同时放全部指挥官。
- Adapter 对所有玩家批量解锁单位。
- 地图本地 XML 覆盖指挥官数据却难以定位来源。
- 运行时为了补字段不断追加 `TechTreeUnitAllow` 和 `CatalogFieldValueSet`。

## 7. 当前项目结构优化建议

### 7.1 RebornBridge 重命名语义

当前 `Mods/Reborn/RebornBridge.SC2Mod` 更像地图族桥接包。

建议长期拆成：

```text
Mods/MapFamilies/RebornHotS/RebornHotSData.SC2Mod
Mods/MapFamilies/RebornHotS/RebornHotSAdapter.SC2Mod
```

短期可以保留现名，但文档和 manifest 中明确：

- `RebornBridge` 不拥有指挥官数据。
- `RebornBridge` 只放地图族共享补丁。
- `RebornMapAdapter` 只放生命周期和玩家槽位适配。

### 7.2 CommanderUnits_* 逐步改造

当前 `Mods/7vs1/CommanderUnits_*.SC2Mod` 已经接近 CommanderDataCenter，但仍受 7vs1 命名和依赖影响。

建议迁移路径：

1. 保持现有包不动，先为每个包增加 `Shared/Commanders/*.json` 所有权清单。
2. 为 Raynor 试点创建数据空间入口 `GameData.xml`。
3. 把 Raynor 数据按 Units、Abilities、Buttons、Actors、Effects、Behaviors、Upgrades 分类。
4. 确认 toolkit trace 能追踪到数据空间来源。
5. 再逐个迁移其他指挥官。

### 7.3 SharedUnits 和 BaseCatalogPatch 拆分

当前共享包容易变成“什么都能放”的垃圾桶。

建议拆为：

```text
PlatformDataCenter
CapabilityDataCenter
SharedAssetRefs
CompatibilityPatch
```

规则：

- 能归指挥官的，归 CommanderDataCenter。
- 能归地图族的，归 MapFamilyDataCenter。
- 真正所有地图和所有指挥官共用的，才归 Platform。
- 临时修复必须带 PairPatch manifest。

### 7.4 测试地图作为数据中心实验场

`光晕测试 by Pirate.SC2Map` 的数据量小，但很适合作为数据空间演示：

```text
HaloSceneData.xml
PsiShadowData.xml
MarineTestData.xml
```

该地图可以作为：

- 数据空间结构 smoke test。
- 编辑器迁移流程样例。
- `GameData.xml <Includes>` 解析器测试样例。
- 后续数据中心生成器的最小 fixture。

注意：该地图当前工作区存在大量删除和未跟踪重建状态，不能在未确认前提交结构迁移。

## 8. 命名规范

### 8.1 文件名

使用：

```text
RaynorUnits.xml
RaynorAbilities.xml
RebornBridgeRequirements.xml
TopPanelButtons.xml
```

避免：

```text
Unit.xml
Actor.xml
新单位.xml
测试.xml
```

### 8.2 Catalog ID

建议前缀：

| 类型 | 前缀示例 |
| --- | --- |
| Platform | `PX_` |
| Capability | `PXHeroRevive_` |
| Commander | `CMRaynor_` 或保留原官方 ID 并声明 owner |
| MapFamily | `MFReborn_` |
| PairPatch | `PPRebornRaynor_` |
| Test | `TestHalo_` |

对已有官方或已迁移 ID，不强制改名，但必须在 owner manifest 中声明。

## 9. 工具链补充

### 9.1 DataSpace linter

新增检查器：

```powershell
node scripts/sc2-composer/cli.mjs lint-dataspaces
```

检查：

- `Base.SC2Data/GameData.xml` 是否存在。
- `<Includes>` 中的文件是否存在。
- 文件名是否 ASCII。
- XML 是否 UTF-8。
- 每个数据空间是否只有一个 `<Catalog>` 根。
- 同一数据中心内部是否有重复 Catalog ID。
- 数据空间引用是否排序稳定。
- 未被 include 的 `GameData/*.xml` 是否需要删除或登记。

### 9.2 DataSpace manifest

每个数据中心配套：

```text
DataCenter.json
```

示例：

```json
{
  "schemaVersion": 1,
  "id": "commander.TerranRaynor",
  "type": "CommanderDataCenter",
  "owner": "TerranRaynor",
  "gameDataEntry": "Base.SC2Data/GameData.xml",
  "spaces": [
    {
      "path": "GameData/RaynorUnits.xml",
      "owns": ["CUnit"],
      "catalogIds": []
    }
  ],
  "exports": {
    "units": [],
    "abilities": [],
    "upgrades": []
  },
  "imports": {
    "capabilities": []
  }
}
```

### 9.3 追踪工具增强

`sc2-editor-toolkit trace` 应显示：

```text
sourcePackage
sourceDataCenter
sourceDataSpace
catalogType
catalogId
fieldPath
mergeAction
winner
```

这样才能判断一个字段来自：

- 指挥官中心。
- 地图族中心。
- PairPatch。
- 地图本地数据。
- Galaxy 运行时。

## 10. 迁移路线

### Phase A：文档和 schema

1. 固化本设计文档。
2. 为 DataCenter.json 创建 schema。
3. 为 `GameData.xml <Includes>` 写 linter。
4. 让 linter 读取真实项目文件。

### Phase B：测试地图样例

1. 选择 `光晕测试 by Pirate.SC2Map` 作为数据空间最小样例。
2. 按 `HaloSceneData`、`PsiShadowData`、`MarineTestData` 拆分。
3. 保持原行为不变。
4. 用 galaxy-checker 和编辑器打开验证。

### Phase C：Raynor CommanderDataCenter

1. 为 `CommanderUnits_Raynor.SC2Mod` 增加数据空间入口。
2. 先只调整 XML 组织，不改变 Catalog ID。
3. 生成 `DataCenter.json`。
4. 用 `trace` 和 `diagnose-unit` 验证兵营、Marine、Marauder、升级和按钮。

### Phase D：Reborn MapFamilyDataCenter

1. 整理 `RebornBridge` 中的共享 Catalog。
2. 拆为 Reborn units、requirements、buttons、actors 等数据空间。
3. 保持 `RebornMapAdapter` 的 Galaxy 生命周期逻辑独立。
4. 对 `zexpedition03` 跑静态和进图验证。

### Phase E：CompositionPlan 接入

1. CompositionPlan 按数据中心输出依赖层。
2. 组合报告列出每个 Catalog ID 的 owner。
3. PairPatch 只能引用 DataCenter manifest 中存在的导出或地图本地字段。

## 11. 验收标准

第一阶段完成时应满足：

- 至少一个测试地图使用数据空间并保持行为不变。
- 至少一个 CommanderDataCenter 使用 `GameData.xml <Includes>`。
- 至少一个 MapFamilyDataCenter 使用数据空间。
- `lint-dataspaces` 能检查真实项目。
- `trace` 能显示数据空间来源。
- 没有因为拆分数据空间产生新的 Catalog 丢失。
- 修改运行时产物时按 `$sc2-workflow` 完成静态检查和进图验证。

## 12. ADR

### 决策

采用“数据中心 + 数据空间 + CompositionPlan”的项目结构。

### 原因

- 指挥官和地图组合会持续增多。
- 单个 XML 文件和共享大包会让所有权越来越模糊。
- 数据空间能把 Catalog 数据按功能拆分，便于迁移、复用和审计。
- CompositionPlan 需要更细粒度的来源信息，才能判断冲突和生成 patch。

### 不采用的方案

**继续维护默认 `GameData/*.xml` 自动加载**

- 简单，但文件会继续膨胀。
- 无法表达数据中心所有权。
- 不利于跨地图复用。

**把所有共享数据放入一个 SharedUnits**

- 初期省事。
- 长期会变成没有边界的公共垃圾桶。
- 冲突和回归范围不可控。

**所有数据都拆到地图本地**

- 单图容易成功。
- 无法实现任意指挥官与任意地图组合。
- 更新和修复无法复用。

### 后果

- 需要新增 linter 和 manifest。
- 早期迁移会多一步 XML 拆分和校验。
- 长期可以显著降低冲突定位和跨图复用成本。

## 13. 与现有设计的关系

`指挥官地图组合框架设计.md` 定义组合运行时和依赖层。

本文定义这些依赖层内部如何组织 Catalog 数据：

```text
CommanderPackage
  -> CommanderDataCenter
  -> GameData.xml
  -> DataSpace XML

MapFamilyAdapter
  -> MapFamilyDataCenter
  -> GameData.xml
  -> DataSpace XML

PairPatch
  -> PairPatchDataCenter
  -> GameData.xml
  -> DataSpace XML
```

两份设计应一起执行：

- 组合框架解决“选谁和怎么加载”。
- 数据中心解决“数据放哪、谁拥有、如何迁移和追踪”。

## 16. Galaxy 代码与数据中心的关系

数据中心主要解决 Catalog 数据的组织，但 Galaxy runtime 代码也需要协同，否则会出现"数据归位了但代码还引用旧路径"的问题。

### 16.1 当前 Galaxy 代码的组织问题

```text
CoreRuntime.SC2Mod/
  LibE0EAE146.galaxy                      # 主入口，include 全部指挥官 runtime
  LibE0EAE146_h.galaxy                     # 头文件，暴露全部指挥官函数
  LibE0EAE146_CommanderRegistry.galaxy     # 注册表，逐指挥官分支
  LibE0EAE146_AdapterBootstrap.galaxy      # Adapter 引导，include 全部 Adapter
  LibE0EAE146_RaynorRuntime.galaxy         # Raynor runtime
  LibE0EAE146_AbathurRuntime.galaxy        # Abathur runtime
  ... (共 18+ 个指挥官 runtime)

CommanderUnits_Raynor.SC2Mod/
  LibE0EAE146_RaynorRuntime.galaxy          # 又一份？（实际是同一份复制）

Alenger1Adapter.SC2Mod/
  ComponentList.SC2Components              # 只有占位，无 galaxy
```

问题：

1. **CoreRuntime 编译期 include 全部指挥官**：新增指挥官必须修改 CoreRuntime。
2. **galaxy 文件被复制到地图目录**：启动器为满足 include，把全部 galaxy 复制到地图 `Base.SC2Data/`。
3. **Adapter 没有 galaxy 代码**：`Alenger*Adapter.SC2Mod` 只是 ComponentList 占位，实际 Adapter 逻辑在 CoreRuntime 中。
4. **CommanderUnits_Raynor 的 galaxy 和 catalog 在同一个 mod**：数据空间迁移时需要同时处理 galaxy。

### 16.2 Galaxy 代码的目标组织

Galaxy 代码遵循"代码跟随 owner"原则：

```text
Mods/Commanders/Raynor/Raynor.SC2Mod/
  Base.SC2Data/
    GameData.xml                           # 数据空间主入口
    GameData/
      RaynorUnits.xml                      # Catalog 数据
      RaynorAbilities.xml
      ...
    LibE0EAE146_RaynorRuntime.galaxy       # Galaxy runtime（跟随 owner）
    LibE0EAE146_RaynorRuntime_h.galaxy
```

PlatformKernel 只 include 通用 capability 库，不 include 具体指挥官：

```text
Mods/Platform/PlatformKernel.SC2Mod/
  Base.SC2Data/
    LibPLATFORM.galaxy                     # 主入口，只 include capability
    LibPLATFORM_h.galaxy
    LibPLATFORM_HeroRevive.galaxy          # 通用英雄复活
    LibPLATFORM_TopPanel.galaxy            # 通用顶栏
    LibPLATFORM_CatalogSafety.galaxy       # Catalog 安全修改封装
```

### 16.3 组合生成 bootstrap

由于 Galaxy 静态 include 限制，每个组合生成只 include 选中指挥官的 bootstrap：

```galaxy
// LibCOMPOSITION_<hash>.galaxy（生成产物）
include "LibPLATFORM"
include "LibE0EAE146_RaynorRuntime"        // 只 include 选中的指挥官
include "LibRebornMapAdapter"              // 只 include 选中的 MapAdapter

void LibCOMPOSITION_Init() {
    LibPLATFORM_Init();
    libE0EAE146_gf_RaynorRuntime_Init();
    libRebornMapAdapter_gf_Init();
}
```

### 16.4 迁移策略

Galaxy 代码迁移分两步：

1. **短期（Phase C-E）**：保持 CoreRuntime 全量 include，但 CommanderUnits 包内 galaxy 文件和 catalog 数据归位到数据空间结构。启动器继续复制 galaxy 到地图目录。
2. **长期（Phase F+）**：引入 CompositionCompiler 生成 bootstrap，CoreRuntime 不再 include 具体指挥官，启动器不再复制全量 galaxy。

## 17. 风险与缓解

### 17.1 数据空间迁移破坏 Catalog 加载

**风险**：SC2 编辑器中数据迁移到数据空间后，如果 `GameData.xml` 的 `<Includes>` 路径错误或文件名包含非 ASCII 字符，会导致 Catalog 静默丢失。

**缓解**：
- `lint-dataspaces` 必须在每次提交前运行。
- 迁移后用 `sc2-editor-toolkit trace` 验证每个 Catalog ID 仍然可追踪。
- 迁移后进图验证，确认单位/技能/按钮存在。
- 单次迁移只处理一个数据中心，不批量操作。

### 17.2 Galaxy include 链断裂

**风险**：数据空间迁移时如果误改 galaxy 文件位置，会导致 ScriptError（如本次 Reborn 地图的 `Lib67C0F0E7` include 失败）。

**缓解**：
- 数据空间迁移只处理 Catalog XML，不改动 galaxy 文件位置。
- galaxy 文件位置变更必须独立提交，并运行 galaxy-checker。
- 迁移后启动测试，检查 `GameLogs/*ScriptError.txt`。

### 17.3 启动器 Clean 函数误删地图自带库

**风险**：启动器 Clean 函数无差别删除 `Lib*.galaxy`，会误删地图自带的库文件（已在 Reborn 地图中发生过）。

**缓解**：
- Clean 函数必须构建源地图 galaxy 文件白名单（已在 `launch-reborn-commander.ps1` 修复）。
- 长期目标是启动器不再删除任何 galaxy 文件，由 CompositionPlan 精确控制注入。

### 17.4 数据中心数量爆炸

**风险**：如果每个指挥官、每个地图族、每个组合都有数据中心，数量会迅速增长。

**缓解**：
- PairPatch 必须有明确的 `reason` 字段和验证条件。
- 定期审查 PairPatch 数量，架构健康指标 `pair_patch_count` 增长速度必须低于组合数量增长速度。
- 能归 Commander 的归 Commander，能归 MapFamily 的归 MapFamily，PairPatch 是最后例外。

### 17.5 数据空间与默认自动加载混用

**风险**：部分包使用数据空间（`GameData.xml <Includes>`），部分包使用默认自动加载（`GameData/*.xml` 全部加载），可能导致同一 Catalog 被加载两次或加载顺序异常。

**缓解**：
- `lint-dataspaces` 检查同一 mod 内是否同时存在 `GameData.xml <Includes>` 和未被引用的 `GameData/*.xml`。
- 迁移一个数据中心时，必须完整迁移，不保留半迁移状态。
- 迁移期间允许"未迁移的包继续自动加载"，但必须在 `DataCenter.json` 中标记 `migrationStatus: "pending"`。

### 17.6 RebornBridge 身份模糊

**风险**：`RebornBridge.SC2Mod` 当前既是 MapFamilyDataCenter 又包含部分 MapAdapter 逻辑，身份不清。

**缓解**：
- 短期：在文档和 manifest 中明确 `RebornBridge` 只放地图族共享数据。
- 长期：拆分为 `RebornHotSData.SC2Mod`（数据）和 `RebornHotSAdapter.SC2Mod`（生命周期）。
- 拆分时必须进图验证 Reborn 任务 AI、剧情、胜负不变。
