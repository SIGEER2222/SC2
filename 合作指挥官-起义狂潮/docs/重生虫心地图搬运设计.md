## 1. 结论摘要

本次搬运不采用“把重生虫心主 Mod 直接叠加到现有 7vs1 依赖”的方式。

推荐采用两条相互隔离的交付线：

1. **原版基线线**
   - 保留重生虫心五个 Mod 的完整依赖闭包。
   - 地图和 Mod 不做语义改写，只做安装、路径校验、依赖校验和启动验证。
   - 用于证明原包在当前游戏环境中可以正常运行，并建立后续修改的对照基线。
2. **兼容搬运线**
   - 从原版地图生成独立工作副本。
   - 使用专用 `RebornBridge.SC2Mod` 和逐地图 patch 适配现有运行时、指挥官单位与科技体系。
   - 不修改原始地图，不覆盖原版 Reborn bundle。

选择该方案的原因：

- 重生虫心主 Mod 约有 5,554 个唯一 Catalog 条目。
- 与当前 `Mods/7vs1` 存在 490 个同类型、同 ID 冲突。
- 重生虫心脚本存在大量运行时科技、能力和 Catalog 修改。
- SC2 地图本地数据最终仍可覆盖依赖项，单靠公共 Mod 无法解决所有地图差异。
- 先建立可运行原版基线，才能区分“原图已有问题”和“搬运引入问题”。

第一张试点图建议使用 `zexpedition03`，备选为 `zhybrid01`。两张图本地 Catalog 规模小，与当前 7vs1 的本地 ID 重叠为 0，且各自只有一个 Galaxy 脚本。

## 2. 目标与非目标

### 2.1 目标

- 完整识别重生虫心地图、Mod、资产、Galaxy 库和剧情进度依赖。
- 建立可重复执行的安装、分析、转换、启动、验证流程。
- 保证原版地图能作为稳定基线直接启动。
- 支持逐张地图生成兼容搬运版本，而不是手工修改唯一副本。
- 解决或提前发现以下高频问题：
  - 兵营等生产建筑无法训练预期单位。
  - 单位创建成功但缺少技能、按钮、武器或升级。
  - 静态 GameData 查询结果与进图后的运行时单位不一致。
  - 依赖项按 ID 覆盖导致科技、单位或行为退化。
  - 触发器重新保存后产生脚本 ID、编码或乱码问题。
  - 文件型 MPQ Mod 未被同步，导致依赖闭包不完整。
- 为后续批量迁移提供机器可读 manifest、诊断报告和验收记录。

### 2.2 非目标

- 本阶段不直接修改 30 张地图。
- 不把重生虫心全部数据合并进 `CoreRuntime`、`CommanderUnits_*` 或 `XM`。
- 不在第一阶段统一重写所有触发器。
- 不把 216 MB 资产包直接作为普通 Git blob 提交。
- 不假设“自定义对战可用”等同于“战役图可用”。
- 不用 `launch-7vs1-coop-test.ps1` 启动原始 Reborn 地图。

## 4. 核心风险

### 4.1 依赖项不是简单的资源引用

SC2 的依赖项参与数据继承和覆盖：

- 父级依赖中存在的数据会被后加载依赖和地图本地数据继承或覆盖。
- 同一 Catalog 类型、同一 ID 的条目会发生合并或覆盖。
- 子对象未声明的字段可能继续继承父对象。
- 地图本地 GameData 的优先级高于公共依赖。
- Galaxy 运行时仍可再次修改单位、能力、科技和 Catalog 字段。

因此，“某个 Mod 在自定义对战可用”不能证明它在战役地图中可用。战役图可能通过本地数据、触发器、Bank 或官方 Campaign 状态再次改变最终结果。

### 4.2 Catalog 冲突

重生虫心主 Mod 与当前 `Mods/7vs1` 存在 490 个同 tag、同 ID 条目冲突，主要包括：

| Catalog 类型 | 冲突数 |
| --- | ---: |
| `CUnit` | 156 |
| `CButton` | 102 |
| `CActorUnit` | 26 |
| `CRequirement` | 25 |
| `CAbilEffectInstant` | 25 |
| `CBehaviorBuff` | 24 |
| `CWeaponLegacy` | 14 |
| `CUpgrade` | 6 |

此外，Reborn 还覆盖 `CGame id="Dflt"`。这类全局对象一旦后加载，影响范围不只是一张地图或一个单位。

结论：

- 禁止直接把整个 Reborn 主 Mod 作为 7vs1 的后加载依赖。
- 冲突必须按“保留 Reborn、保留 7vs1、桥接合并、地图特例”分类处理。
- `CUnit`、`CAbil*`、`CRequirement`、`CUpgrade` 和 `CGame` 必须优先审计。

### 4.3 运行时差异

Reborn Galaxy 中已发现的动态行为：

| 调用 | 次数 | 影响 |
| --- | ---: | --- |
| `TechTreeUnitAllow` | 640 | 单位是否可训练、建造或使用 |
| `TechTreeAbilityAllow` | 400 | 能力是否被科技树启用 |
| `UnitAbilityAdd` | 50 | 给运行时单位追加技能 |
| `CatalogFieldValueSet*` | 53 | 动态修改 Catalog 字段 |
| `UnitCreate` | 525 | 直接创建运行时单位 |
| CreateUnits 包装调用 | 1,250 | 批量创建单位 |

因此单位诊断必须同时观察三个层次：

1. **静态原始层**：单个 Mod 或地图自己声明的 XML。
2. **依赖合并层**：官方依赖、Reborn bundle、兼容 Mod 和地图本地数据合并后的有效 Catalog。
3. **运行时层**：Galaxy、触发器、Bank 和科技过滤器执行后的实际状态。

只查询静态 XML，无法可靠回答“兵营为什么造不出兵”或“单位为什么没有技能”。

### 4.4 触发器与编码风险

已知高风险行为：

- 中文变量名、触发器名或路径可能在脚本 ID 生成过程中变成乱码。
- 启用“按名字获取/更换脚本 ID”后，中文名称更容易导致不可保存或脚本损坏。
- 翻译包可能把本地化文本注入地图，改变地图内容。
- 用不同语言版本编辑器重新保存地图，可能产生与原版无关的大范围差异。

处理原则：

- 原版基线阶段不使用编辑器重新保存地图。
- 内部变量名、函数名、脚本 ID、目录名统一使用 ASCII 字母、数字和下划线。
- 中文只用于本地化显示文本，不用于内部标识符。
- 必须编辑触发器时，优先使用英文编辑器环境。
- 如果编辑器提供“根据名称生成脚本 ID”选项，中文工程中应关闭。
- 每次触发器改动后对比生成的 Galaxy 文件和触发器数据，禁止只看编辑器能否打开。

## 5. 方案比较

### 5.1 方案 A：原包隔离归档并直接启动

做法：

- 保留五个原始 Mod。
- 保留 30 张原始地图。
- 安装到游戏可解析的 `Mods/`、`Maps/` 路径。
- 使用 `SC2Switcher_x64.exe` 直接启动。

优点：

- 风险最低。
- 最容易建立原版运行基线。
- 能明确判断源包自身是否完整。

缺点：

- 无法使用现有 7vs1 指挥官和运行时。
- 不能解决双方数据叠加需求。

结论：必须实现，但只作为基线和回归对照。

### 5.2 方案 B：原包隔离 + RebornBridge + 地图变体

做法：

- 原包只读保存。
- 生成独立兼容地图副本。
- 公共差异放入 `RebornBridge.SC2Mod`。
- 地图特有差异放入逐地图 patch。
- 由生成器维护依赖顺序、DocumentInfo、DocumentHeader 和 patch manifest。

优点：

- 保留原版基线。
- 公共兼容逻辑可复用。
- 地图特例有明确边界。
- 可以逐张迁移、逐张回滚。
- 适合自动化诊断和批量生成。

缺点：

- 需要先补齐 bundle 安装器、冲突分类器和运行时诊断能力。
- 不能完全依靠一个公共桥接 Mod，仍需逐图 patch。

结论：推荐作为正式搬运架构。

### 5.3 方案 C：直接合并进 CoreRuntime 或 CommanderUnits

做法：

- 把 Reborn 的单位、能力、科技和脚本直接并入现有公共 Mod。

问题：

- 490 个 Catalog 冲突会扩大现有公共 Mod 的行为表面积。
- 大量运行时修改很难证明不会影响其他地图。
- 地图本地覆盖仍然存在，合并后也不能保证最终有效。
- 后续更新 Reborn 或 7vs1 时很难重新同步。
- 回归范围会扩展到所有 7vs1 地图。

结论：否决。

## 6. 架构决策

### ADR-001：采用双轨、生成式搬运

**决策**

采用方案 B，同时把方案 A 作为不可删除的基线。

**约束**

- 原始下载目录永不原地修改。
- 原版容器和兼容容器不能共用同一可写副本。
- 所有兼容修改都必须能由 manifest 或脚本重建。
- 地图最终覆盖公共依赖，因此允许且要求逐地图 patch。

**否决方案**

- 否决直接把 Reborn 后加载到 7vs1。
- 否决把 Reborn 数据整体并入 `CoreRuntime`。
- 否决手工复制一张地图后长期在唯一副本上修改。

## 7. 目标目录与命名

### 7.1 原始源和外部缓存

建议新增外部工作区：

```text
外部资源/
└─ RebornHotS/
   ├─ source-manifest.json
   ├─ sha256sums.json
   ├─ bundle/
   │  ├─ crys_the_swarm_reborn.SC2Mod
   │  ├─ crys_swarm_assets.SC2Mod
   │  ├─ sibirens_starhooks_common.SC2Mod
   │  ├─ sibirens_starhooks_swarmstoryutils.SC2Mod
   │  └─ sibirens_sundries_swarm_reborn.SC2Mod
   ├─ unpacked/
   └─ reports/
```

`bundle/` 可以是本机外部缓存，不要求把大二进制全部提交到 Git。仓库只需提交：

- 文件清单。
- SHA-256。
- 来源说明。
- 安装方式。
- 可公开、可审计的小型文本补丁。

216 MB 资产包优先使用“外部缓存 + SHA-256 manifest”。只有确认远端已配置 Git LFS、配额和团队拉取流程后，才考虑 Git LFS。

### 7.2 项目内地图

为兼容现有地图发现和文档脚本，正式导入的地图保持 ASCII 原名，并放在：

```text
合作指挥官-起义狂潮/Maps/
```

示例：

```text
Maps/zchar01.SC2Map
Maps/zexpedition03.SC2Map
Maps/zstorychar.SC2Map
```

当前 `build-map-docs.mjs` 只扫描 `Maps` 顶层，因此不建议把地图放入 `Maps/RebornCampaign/` 子目录。

兼容版本不使用 `_7vs1` 或 `_xm` 后缀，以免误进入现有依赖替换或启动逻辑。建议使用：

```text
zexpedition03_reborn_port.SC2Map
```

并为其建立独立的 `reborn-integrated` workflow profile。

### 7.3 项目内 Mod

基线安装位置保持源地图声明的 sibling 结构：

```text
合作指挥官-起义狂潮/Mods/
├─ crys_the_swarm_reborn.SC2Mod
├─ crys_swarm_assets.SC2Mod
├─ sibirens_starhooks_common.SC2Mod
├─ sibirens_starhooks_swarmstoryutils.SC2Mod
└─ sibirens_sundries_swarm_reborn.SC2Mod
```

不能只复制 `crys_the_swarm_reborn.SC2Mod`。主 Mod 依赖其余四个 sibling 包，缺少任意一个都不能视为安装成功。

兼容桥接层建议放在：

```text
合作指挥官-起义狂潮/Mods/Reborn/RebornBridge.SC2Mod
```

桥接层不能替代原 Reborn bundle，只处理明确分类后的兼容差异。

## 8. 依赖模型

### 8.1 原版基线

原版地图保持自己的依赖关系，逻辑顺序为：

```text
官方 Campaign / 官方 Mod
  -> Reborn 资产与 helper Mod
  -> crys_the_swarm_reborn.SC2Mod
  -> 地图本地 GameData / Triggers / Galaxy
```

工作流配置需要补充：

```text
file:Campaigns/SwarmStory.SC2Campaign
```

当前 `Shared/Workflow/sc2-workflow.json` 只把 LibertyStory、Void Campaign、Liberty 和 Void 视为 external，直接 inspect Reborn 地图会把 SwarmStory 和 Reborn Mod 报为 unresolved。

### 8.2 兼容搬运版本

兼容版本建议逻辑顺序：

```text
官方 Campaign / 官方 Mod
  -> Reborn 五 Mod
  -> 选定的 7vs1 Runtime / CommanderUnits
  -> RebornBridge.SC2Mod
  -> 逐地图 patch
  -> 地图本地触发器和运行时逻辑
```

该顺序只是设计起点，必须通过 Catalog effective diff 验证。尤其要关注：

- `CGame Dflt`
- 单位生产能力
- CardLayouts 与按钮
- Requirement
- Upgrade
- 科技树 allow/block
- 运行时 `UnitAbilityAdd`
- `CatalogFieldValueSet*`

如果某个冲突无法在公共 Bridge 中稳定解决，应下沉到逐地图 patch；如果不同地图需要互斥语义，不应强行抽成公共覆盖。

## 9. 有效单位诊断模型

为解决生产、技能和静态/运行时不一致问题，每个重点单位应生成一份有效状态报告：

```text
effective-unit-report/<map>/<unit-id>.json
```

报告至少包含：

### 9.1 身份与来源

- 最终单位 ID。
- 父级 ID 和完整继承链。
- 每个字段最后由哪个 Mod 或地图覆盖。
- 是否存在同类型同 ID 冲突。

### 9.2 生产链

- 哪个建筑或单位生产它。
- 使用的 `CAbilTrain` / `CAbilBuild`。
- `InfoArray` 索引和最终 Unit 值。
- CardLayouts 中对应按钮。
- Button 的 AbilityCommand。
- Requirement、科技和资源条件。
- `TechTreeUnitAllow` 最终状态。

### 9.3 技能链

- 静态 `AbilArray`。
- 从父级继承的能力。
- CardLayouts 可见技能。
- 运行时 `UnitAbilityAdd` / `UnitAbilityRemove`。
- `TechTreeAbilityAllow` 最终状态。
- 技能存在但无按钮、按钮存在但能力缺失等不一致。

### 9.4 战斗链

- 武器。
- Effect 链。
- Behavior。
- Upgrade 影响。
- `CatalogFieldValueSet*` 的运行时字段覆盖。

### 9.5 结论

每个报告输出机器可判定状态：

- `complete`
- `missing_train_entry`
- `missing_button`
- `missing_ability`
- `blocked_by_requirement`
- `blocked_by_techtree`
- `runtime_only`
- `catalog_overridden`
- `needs_runtime_probe`

`sc2_unit_explorer.py` 现有能力可以覆盖继承、生产关系、CardLayouts、部分运行时科技和 `UnitAbilityAdd`；后续需优先补：

1. `CatalogFieldValueSet*` 解析。
2. 更精确的 Galaxy 控制流和作用域推断。
3. `ApplyTechFilter` 或等价科技过滤模拟。
4. 地图目录和 Mod bundle 的联合分析。
5. 运行时 probe 与静态报告合并。

## 10. 安装与生成工具

不继续为每张图编写独立复制脚本。应建设统一的 `reborn-port` 工具链。

### 10.1 Bundle 安装器

职责：

- 从 source manifest 读取五个 Mod。
- 同时支持目录型 Mod 和 MPQ 文件型 Mod。
- 递归解析 `DocumentInfo` 和 `DocumentHeader`。
- 安装完整依赖闭包。
- 保持 sibling 相对路径。
- 校验 SHA-256。
- 检测缺失依赖和同名旧文件。
- 输出安装报告，不静默保留错误的 live copy 元数据。

当前缺口：

- `web-launcher/lib/sync-mods-and-maps.mjs` 对 Mod 默认使用目录复制，不能处理四个 MPQ 文件型 Mod。
- 当前 `crys_heart` 场景只同步主 Mod，依赖闭包不完整。
- `launch-crys-heart-map.ps1` 也只覆盖旧单图测试场景，不适合作为 30 图正式搬运器。

### 10.2 容器检查器

对每个地图和 Mod 输出：

- 容器类型：目录或 MPQ。
- 文件数量。
- GameData XML 列表。
- Galaxy/触发器列表。
- 本地化文件列表。
- DocumentInfo/Header 依赖。
- Bank、CampaignData、MissionStatus 调用。
- 文件编码和 BOM 状态。

六张 `zstory*.SC2Map` 必须解包检查，确认：

- 哪张是实际入口。
- 如何选择关卡。
- 如何跳转到任务图。
- 使用哪些 Bank 和 MissionStatus。
- 是否依赖固定地图文件名。

### 10.3 Catalog 冲突分类器

输入：

- Reborn bundle。
- 选定 7vs1 profile。
- 目标地图。

输出：

- 同类型同 ID 冲突。
- 字段级 effective diff。
- 冲突来源和最终赢家。
- 建议分类：
  - `keep_reborn`
  - `keep_7vs1`
  - `bridge_merge`
  - `map_patch`
  - `manual_review`

### 10.4 Galaxy 分析器

使用 `galaxy-checker`，并为地图与五个 Mod 提供完整 symbol roots。

必须检查：

- 语法和语义错误。
- 跨库函数引用。
- 参数数量。
- 禁用 native。
- BOM 和编码。
- Catalog 字符串 ID。

对于 checker 漏掉、但进图出现的 ScriptError：

1. 先为 checker 增加可复现 fixture。
2. 补规则或符号解析能力。
3. 再修地图或脚本。

禁止把静态可发现错误长期留给进图测试。

### 10.5 地图变体生成器

输入：

- 原始地图。
- profile。
- per-map patch manifest。

输出：

- 新地图容器。
- 更新后的 DocumentInfo/Header。
- 必要的 GameData patch。
- 必要的 Galaxy patch。
- 生成报告和哈希。

生成器只改工作副本，不改原图。

## 12. 分阶段迁移

### Phase 0：建立不可变源和清单

产物：

- 35 个容器的路径、类型、大小、SHA-256。
- 五个 Mod 的依赖闭包。
- 30 张地图的依赖和脚本清单。
- 资产包获取说明。
- 原始下载目录只读约定。

完成标准：

- 任意源文件变化都能被哈希检测。
- 可从 manifest 找到每个地图和依赖。

### Phase 1：原版基线安装与启动

工作：

- 实现目录/MPQ 混合 bundle 同步。
- 补充 SwarmStory external dependency。
- 修正 `crys_heart` 场景依赖闭包。
- 接入标准等待脚本。
- 解包六张 story 地图并识别入口协议。

启动方式：

```powershell
$switcher = "E:\SC2\SC2new\StarCraft II\Support64\SC2Switcher_x64.exe"
$map = "<原始或已安装的 Reborn 地图>"
Start-Process -FilePath $switcher -ArgumentList "`"$map`""
```

启动后必须运行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File `
  "E:\Code\MyMod\SC2\合作指挥官-起义狂潮\scripts\wait-for-game-ready.ps1"
```

禁止使用 `launch-7vs1-coop-test.ps1`。该脚本会向非 7vs1 地图注入大量运行时库，可能与原图 `MapScript.galaxy` 冲突。

完成标准：

- 至少一张原版任务图和一张 story 图成功进入。
- 游戏进程存活。
- 等待脚本返回 0。
- 无新增 ScriptError。
- 能确认关卡跳转或入口选择机制。

### Phase 2：建立静态有效数据模型

工作：

- 为生产链、技能链和科技树输出 effective-unit-report。

完成标准：

- 报告可以区分静态缺失、依赖覆盖和运行时注入。

### Phase 3：RebornBridge 最小骨架

工作：

- 创建空的桥接 Mod 骨架。
- 只加入已验证的公共兼容补丁。
- 建立独立 `reborn-integrated` profile。
- 不加入未经分类的批量 Catalog 覆盖。

完成标准：

- 空 Bridge 不改变原版基线行为。
- 添加单个补丁时有对应诊断报告和回归测试。

### Phase 4：低风险试点

## 13. 验收标准

### 13.1 容器与依赖

- 所有源容器有 SHA-256。
- 五个 Reborn Mod 均已安装。
- 目录型和 MPQ 文件型 Mod 都能同步。
- DocumentInfo 和 DocumentHeader 一致。
- 所有 Reborn 自定义依赖可解析。
- 官方 Campaign 被正确识别为 external。

### 13.2 静态检查

- Galaxy checker 扫描目标地图和完整依赖符号根。
- 所有 `[ERROR]` 完整查看。
- 无可修复的：
  - `XLIB_DISALLOWED_NATIVE`
  - `SEM_UNDECLARED_FUNCTION`
  - `SEM_ARGUMENT_COUNT_MISMATCH`
  - `CATALOG_INVALID_UNIT_REF`
  - 编码/BOM 错误
- 剩余跨 Mod 问题必须记录具体来源，不能笼统标记为误报。

### 13.3 运行时检查

- 使用 `SC2Switcher_x64.exe` 直接启动。
- 如果游戏已运行，先重启游戏。
- `wait-for-game-ready.ps1` 返回 0。
- Alerts 出现后 20 秒内无新增 ScriptError。
- 游戏进程持续存活。
- 无“函数已声明但尚未定义”等库冲突。

### 13.4 单位与科技检查

每张任务图至少验证：

- 一个生产建筑。
- 两个预期可训练单位。
- 一个运行时追加技能的单位。
- 一个受升级影响的单位。
- 一个任务脚本直接创建的单位。

每个对象验证：

- 能否生产或创建。
- 按钮是否存在。
- Requirement 是否满足。
- 技能是否存在并可用。
- 科技升级是否作用于正确单位。
- 静态报告与运行时 probe 是否一致。

### 13.5 战役流程检查

- story 图可进入任务图。
- 胜利后状态正确保存。
- 返回枢纽后任务状态正确。
- 失败和重新开始不污染进度。
- 继续游戏可以恢复。
- 中文文本存在，但内部 ID 不因中文发生变化。

## 14. 回滚策略

- 原始下载目录不修改，因此始终可以回到源包。
- 每张兼容地图由 source hash + manifest 生成。
- Bridge 的每个 patch 必须可独立删除。
- 每批地图单独提交，不把 30 张图塞进一个不可审查提交。
- 进图失败时先回退当前地图 patch，不修改公共运行时作为临时补丁。
- 如果公共 Bridge 修改导致其他已迁移地图回归，优先把该逻辑下沉到逐图 patch。

按优先级：

1. `reborn-bundle-inventory`

## 16. 第一实施里程碑

第一里程碑只做“可重复的原版基线”，不接 7vs1：

1. 生成 35 个容器的 SHA-256 manifest。
2. 修复 workflow 对 SwarmStory 的 external dependency 识别。
3. 实现五 Mod 混合容器的闭包安装。
4. 解包并检查六张 `zstory*.SC2Map`。
5. 识别实际剧情入口和 Bank/MissionStatus 协议。
6. 用 `zexpedition03` 建立任务图基线。
7. 用一张 story 图建立剧情入口基线。
8. 将启动、等待、日志和诊断结果写入批次报告。

该里程碑通过后，再创建 `RebornBridge.SC2Mod` 和第一张 `_reborn_port` 兼容地图。这样可以确保后续发现的单位、科技、技能或触发器问题都有稳定对照，不会把源包问题、依赖安装问题和兼容改动问题混在一起。

## 17. 最终决策

本项目的搬运原则不是“让地图尽快加载一次”，而是建立一条可重复、可诊断、可回滚的战役迁移流水线。

最终采用：

- 原版 Reborn bundle 完整保留。
- 原图只读，兼容图由工具生成。
- 公共问题进入 `RebornBridge`。
- 地图特例进入 per-map patch。
- 静态 Catalog、依赖合并结果和 Galaxy 运行时状态统一诊断。
- 先低风险任务图，再按星球分批，Evolution 和 story 图单独收尾。

该结构能避免按 ID 覆盖、父级继承和地图本地覆盖造成的隐式退化，也能把后续重复且耗费 token 的盘点、对比、生成和验证任务逐步下沉为本地工具。
