# 系统结构与工作流优化设计

> 日期：2026-07-11
> 范围：`合作指挥官-起义狂潮` 项目结构、数据流、启动流、验证流、文档流、低成本任务流
> 目标：把当前“多入口、多脚本、多事实源”的项目，收敛为围绕 `CompositionPlan`、`DataCenter`、`MapProfile`、`CommanderPackage` 的可执行工程系统。

## 1. 当前结论

项目已经从“修一张图/修一个指挥官”的阶段，进入“组合平台雏形”阶段。当前已经具备：

- `Shared/Commanders`：指挥官元数据雏形。
- `Shared/Launcher`：Reborn 启动器配置。
- `Shared/Maps/maps.json`：旧地图元数据集合。
- `scripts/sc2-composer`：数据中心 linter、CompositionPlan schema、CommanderPackage schema、依赖解析骨架。
- `scripts/sc2-launcher`：Reborn 启动器共享模块、配置校验、launcher-plan、DocumentHeader/DocumentInfo roundtrip。
- `scripts/sc2-editor-toolkit`：依赖检查、Catalog trace、unit diagnosis 的主诊断工具。
- `docs/低成本模型任务包`：可下放批量证据收集任务。
- `docs/经验总结`：阶段性经验沉淀。

但系统的结构性问题仍然明显：

1. 事实源仍然分散：`Shared/Launcher`、`Shared/Commanders`、`Shared/Maps/maps.json`、旧启动器、Web launcher 各自维护一部分组合事实。
2. `sc2-composer` 和 `sc2-launcher` 已经出现重叠：一个是目标规划器，一个是过渡启动执行器，但边界还没有完全固定。
3. 旧 `launch-7vs1-coop-test.ps1` 仍保留大量硬编码 commander 映射和全量依赖 fallback。
4. Reborn 启动器虽然已经有 plan/dry-run/roundtrip，但仍直接计算 Galaxy 注入、依赖层和 live 同步。
5. Web launcher 仍是单体入口，后续应消费 plan，而不是自己推导地图/指挥官参数。
6. 文档很多，但缺少一份“当前系统怎么走一次完整工作流”的执行总线说明。
7. 低成本模型任务已经有方向，但还没有完全标准化输入/输出契约。

本设计的核心方向：

```text
Shared/* + DataCenter.json + MapProfile + CommanderPackage
        ↓
scripts/sc2-composer 生成 CompositionPlan
        ↓
scripts/sc2-launcher / web-launcher 只执行 CompositionPlan
        ↓
scripts/sc2-editor-toolkit + runtime probes 验证行为
        ↓
docs/经验总结 + fixtures 捕获新失败模式
```

## 2. 当前系统分层

### 2.1 数据层

数据层保存事实，不执行组合决策。

当前主要目录：

```text
合作指挥官-起义狂潮/
├─ Mods/                         # SC2Mod 数据与 Galaxy runtime
├─ Maps/                         # 地图源、试点图、生成/解包图
├─ Shared/
│  ├─ Commanders/                # CommanderPackage 雏形
│  ├─ Launcher/                  # Reborn 过渡启动配置
│  ├─ Maps/maps.json             # 旧地图元数据
│  ├─ Talents/                   # 天赋数据
│  ├─ CommanderPower/            # 威望/精通/指挥官能力元数据
│  └─ Workflow/sc2-workflow.json # 旧 workflow 配置
└─ docs/
```

问题：

- `Shared/Launcher` 与 `Shared/Commanders` 存在重复 commander 映射。
- `Shared/Maps/maps.json` 是旧扁平模型，不能表达 MapProfile 所需的玩家槽位、Bank、生命周期 hook、地图所有权。
- 旧 `Shared/Workflow/sc2-workflow.json` 仍可能和新 CompositionPlan 并行存在。
- `Mods/*/DataCenter.json` 已开始承担 owner 声明，但还没有成为所有工具统一读取的硬依赖。

目标：

- `Shared/Commanders/*.json` 成为指挥官身份和 CommanderPackage 的唯一入口。
- `Shared/Maps/profiles/<family>/<map-id>.json` 成为地图契约唯一入口。
- `Mods/**/DataCenter.json` 成为 Catalog/Galaxy 数据中心 owner 唯一入口。
- `Shared/Launcher/*.json` 只保留 compatibility shim 所需的临时配置，并标记迁移终点。

### 2.2 编译规划层

规划层只计算计划，不写 live 目录，不启动游戏。

当前主要目录：

```text
scripts/sc2-composer/
├─ cli.mjs
├─ schema/
│  ├─ CommanderPackage.schema.json
│  ├─ CompositionPlan.schema.json
│  ├─ DataCenter.schema.json
│  └─ MapProfile.schema.json
├─ src/
│  ├─ commanderPackage.mjs
│  ├─ compositionPlan.mjs
│  ├─ lintDataspaces.mjs
│  └─ xmlLite.mjs
└─ tests/
```

已有能力：

- lint 数据空间和 DataCenter manifest。
- 校验 CommanderPackage。
- 校验 CompositionPlan。
- 解析依赖层骨架。

问题：

- `compositionPlan.mjs` 当前仍是骨架，依赖层只覆盖一部分。
- 还没有统一读取 `Shared/Launcher` 过渡配置并转为 CompositionPlan 的正式入口。
- 还没有 build/generate bootstrap 阶段。
- 还没有把 Catalog 冲突、Galaxy injection、Document rewrite、runtime probe 全部放进 plan。

目标：

```text
sc2-composer plan
  输入：map id + slot commander + options
  输出：CompositionPlan.json

sc2-composer build
  输入：CompositionPlan.json
  输出：生成地图副本、bootstrap、patch manifest

sc2-composer validate
  输入：CompositionPlan.json
  输出：静态验证、数据中心验证、Galaxy checker 摘要

sc2-composer launch
  输入：CompositionPlan.json
  委托 launcher 执行，不重新计算事实
```

### 2.3 执行层

执行层消费计划，负责同步文件、写生成副本、启动 SC2、收集日志。

当前主要目录：

```text
scripts/sc2-launcher/
├─ common.ps1
├─ mod-sync.ps1
├─ map-sync.ps1
├─ config-validation.ps1
├─ document-dependencies.ps1
├─ launcher-plan.ps1
├─ schema/
└─ tests/

scripts/reborn/launch-reborn-commander.ps1
scripts/launch-7vs1-coop-test.ps1
```

已有能力：

- Reborn 启动器支持 `-CheckOnly`、`-DryRun`。
- Reborn 启动器可输出 launcher-plan 和 baseline。
- 配置校验已开始硬失败。
- DocumentHeader/DocumentInfo roundtrip 已抽出工具。

问题：

- Reborn 启动器仍在自己计算 plan。
- `launcher-plan.ps1` 内仍通过目录扫描构造 Galaxy 注入列表。
- `Export-LauncherPlan` 写 `out/compositions`，但计划还不是全项目唯一入口。
- `launch-7vs1-coop-test.ps1` 仍有 commander 映射、全量 fallback、依赖拼接等旧逻辑。
- PowerShell 执行层仍和 repo 特定路径、SC2 live 路径耦合较深。

目标：

- 启动器只执行 `CompositionPlan` 或 `LauncherCompatibilityPlan`。
- 任何 `Commander`、`MapName` 直参最终都先转成 plan，再执行。
- `launch-7vs1-coop-test.ps1` 进入 compatibility mode，逐步由 plan runner 替代。
- live 同步和 map 生成必须有可重复报告。

### 2.4 诊断验证层

验证层判断“能启动”之外的真实行为。

当前主要入口：

```text
scripts/sc2-editor-toolkit/cli.mjs
scripts/galaxy-checker/
scripts/wait-for-game-ready.ps1
scripts/check-game-logs.ps1
scripts/sc2-composer/cli.mjs lint-dataspaces
scripts/sc2-launcher/tests/document-dependencies.test.ps1
```

关键原则：

- 依赖链是父模型，地图本地最后覆盖。
- 单位行为问题必须跑 `diagnose-unit`，不能只看 XML。
- 无 ScriptError 只是启动 smoke，不等于行为正确。
- 运行时空日志不等于没有动态 mutation。

问题：

- 验证入口分散，缺少一个组合级验证命令。
- 低成本批量任务输出与主工具输出还没有统一 schema。
- 运行时 probe 尚未成为 CompositionPlan 的标准字段。

目标：

```text
sc2-composer verify --plan <plan>
  1. schema
  2. datacenter
  3. dependency closure
  4. galaxy checker
  5. document roundtrip
  6. unit diagnostics
  7. runtime smoke
  8. runtime probe
  9. evidence report
```

### 2.5 Web/UI 层

当前 `web-launcher/app.js` 体积较大，Web 入口还没有完全绑定 CompositionPlan。

问题：

- Web 可能继续自己维护地图/指挥官/参数转换逻辑。
- Web 参数构造和 CLI/PowerShell 启动器容易漂移。
- Web 里的地图分类、Tab、场景配置和 `Shared/Maps`、MapProfile 之间边界不清。

目标：

- Web 只负责选择输入：map、slot、commander、威望、精通、突变、天赋。
- Web 调 `sc2-composer plan` 生成 plan preview。
- Web 调 launcher 执行 plan。
- Web 不直接拼 DocumentHeader 依赖、不直接计算 CommanderUnits、不直接推导 Galaxy 注入。

## 3. 推荐目标架构

### 3.1 总线模型

系统应围绕一个中间产物运转：

```text
CompositionPlan
```

所有入口统一为：

```text
输入意图
  mapProfileId
  slots
  commander options
  launch profile
        ↓
sc2-composer plan
        ↓
CompositionPlan.json
        ↓
执行器 / Web / 验证器 / 文档报告
```

### 3.2 事实所有权

| 事实 | 唯一 owner | 当前过渡来源 | 目标 |
| --- | --- | --- | --- |
| 指挥官身份 | `Shared/Commanders/*.json` | `_registry.json` + launcher mapping | CommanderPackage |
| 指挥官 mod 路径 | CommanderPackage / DataCenter | `commander-units-mapping.json` | DataCenter reference |
| 地图契约 | MapProfile | `Shared/Maps/maps.json` + Reborn config | `Shared/Maps/profiles` |
| 地图族依赖 | MapProfile + MapFamily DataCenter | `reborn-dependencies.json` | CompositionPlan |
| Catalog owner | `DataCenter.json` | `DataCenter.json` 已存在但未完全强制 | DataCenter hard gate |
| Galaxy 编译依赖 | GalaxyManifest / generated bootstrap | launcher 目录扫描 | plan field |
| DocumentHeader/Info | Plan build output | launcher rewrite | plan build step |
| 启动 live 同步 | Launcher execution report | PowerShell script | plan execution report |
| 验证证据 | VerificationReport | docs/经验总结 + logs | machine-readable report |

## 4. 工作流优化设计

### 4.1 标准组合工作流

一次“让某指挥官进入某地图”的标准流程：

```text
Step 0 Intake
  明确 mapProfile、commander slot、options、验证等级

Step 1 Inventory
  读取 MapProfile、CommanderPackage、DataCenter、GalaxyManifest

Step 2 Plan
  生成 CompositionPlan

Step 3 Static Validate
  schema、依赖闭包、数据中心、Galaxy checker、Document roundtrip

Step 4 Build
  生成地图副本、bootstrap、local patch、DocumentHeader/Info

Step 5 Launch
  同步 live mod/map，写 Bank，启动 SC2，等待 ready

Step 6 Runtime Probe
  检查单位、科技、技能、UI、Bank、胜负、ScriptError

Step 7 Report
  输出 VerificationReport

Step 8 Capture
  新失败模式转成 schema、fixture、linter、unit diagnostic case
```

### 4.2 文档工作流

当前文档已经很多，后续应区分三类：

```text
设计文档
  说明目标结构和长期原则，不记录流水账

执行计划
  可直接拆任务，包含产物路径、命令、验收标准

经验总结
  记录当天发现、失败模式、修复证据、commit
```

推荐命名：

```text
docs/架构/组合平台系统结构.md
docs/架构/CompositionPlan契约.md
docs/经验总结/YYYY-MM-DD_<主题>.md
docs/低成本模型任务包/<batch>/<task>.md
```

### 4.3 低成本模型任务工作流

低成本任务必须避免要求模型做 owner 判断，只做批量证据收集。

任务包标准输入：

```yaml
taskId: 01-galaxy-include-inventory
scope:
  roots:
    - Mods/7vs1/CoreRuntime.SC2Mod
    - Mods/7vs1/CommanderUnits_Raynor.SC2Mod
inputs:
  files:
    - ...
rules:
  readOnly: true
  noJudgement: true
outputs:
  format: json + markdown summary
  requiredFields:
    - scannedFiles
    - findings
    - incompleteReasons
```

任务包标准输出：

```text
docs/低成本模型产物/<task-name>/<batch-id>/
  result.json
  summary.md
  raw/
```

主流程只采纳：

- 文件列表。
- 计数。
- 错误码。
- 明确证据。
- `complete: false` 的缺口。

主流程不采纳：

- owner 判断。
- 架构决策。
- “看起来应该”的推断。
- 未验证的兼容结论。

### 4.4 Skill / AGENTS 工作流

当前顶层规则信息量偏大，建议分层：

```text
AGENTS.md
  只保留全仓库硬规则：
  - 先 git status
  - 文件写入方式
  - 提交/推送规则
  - SC2 任务必须用 sc2-workflow

.codex/skills/sc2-workflow/
  放 SC2 依赖、诊断、验证流程

.codex/skills/file-operations/
  放禁止 shell 写入、使用 apply_patch 的规则

docs/架构/
  放系统设计，不塞进 AGENTS

docs/低成本模型任务包/
  放批量任务模板
```

优化点：

- AGENTS 不应重复设计文档内容。
- 技术长说明放 skill 或 docs。
- “必须遵守”的执行规则放 skill，且每条都能映射到检查项。
- `Out-File`、`Set-Content`、`Add-Content`、重定向、临时脚本写文件这类限制继续保留在 file-operations skill。

## 5. 当前具体优化点

### 5.1 收敛 `Shared/Launcher`

问题：

- `Shared/Launcher` 是 Reborn 过渡配置。
- 它和 `Shared/Commanders`、DataCenter、MapProfile 重复。

改进：

1. 给每个 `Shared/Launcher/*.json` 加 `migrationTarget` 字段。
2. 让 `launcher-plan.ps1` 输出每个字段未来迁移目标。
3. 新增检查：如果同一 commander 在 launcher mapping 和 CommanderPackage 中冲突，硬失败。
4. 当 `sc2-composer plan` 覆盖 Reborn 后，冻结 `Shared/Launcher`，只允许 bugfix。

### 5.2 把 `launcher-plan` 升级为正式兼容计划

问题：

- `LauncherCompatibilityPlan` 已存在，但还不是全系统 contract。

改进：

1. 将 `launcher-plan.schema.json` 与 `CompositionPlan.schema.json` 对齐字段命名。
2. 增加 `sourceDataCenter`。
3. 增加 `sourceManifest`。
4. 增加 `executionMode: legacy-launcher | generated-bootstrap`。
5. 增加 `knownDebt`：

```json
{
  "knownDebt": [
    {
      "id": "core-runtime-full-include",
      "reason": "CoreRuntime hardcodes all commander runtime includes",
      "removalCondition": "generated bootstrap passes Raynor/Kerrigan/Karax"
    }
  ]
}
```

### 5.3 建立 GalaxyManifest

问题：

- 当前 Galaxy 注入仍靠 `sourcePatterns` 扫描。

改进：

新增：

```text
Shared/Galaxy/reborn-compat-galaxy-manifest.json
Shared/Galaxy/galaxy-manifest.schema.json
```

字段：

```json
{
  "schemaVersion": 1,
  "id": "reborn.compat",
  "entries": [
    {
      "file": "Base.SC2Data/LibE0EAE146_RaynorRuntime.galaxy",
      "owner": "Commander.TerranRaynor",
      "sourceMod": "Mods/7vs1/CommanderUnits_Raynor.SC2Mod",
      "compileProvides": ["LibE0EAE146_RaynorRuntime"],
      "compileRequires": [],
      "reason": "selected commander runtime",
      "compatibilityOnly": false
    }
  ]
}
```

完成标准：

- 注入清单不再来自目录扫描。
- 未声明文件禁止注入。
- 每个 compatibility-only 文件有移除条件。

### 5.4 改造旧 7vs1 启动器

问题：

- `launch-7vs1-coop-test.ps1` 保留旧映射和全量 fallback。

改进：

1. 增加 `-Plan` 参数。
2. 无 `-Plan` 时生成 compatibility plan。
3. 把 `Get-CommanderUnitsModName` 改为读取 CommanderPackage 或 launcher mapping。
4. 禁止“未指定指挥官返回全量依赖”作为默认行为，改为显式 `-LegacyAllCommanders`。
5. 输出 execution report。

### 5.5 Web launcher 只消费 plan

问题：

- Web 入口体量大，容易继续维护独立事实。

改进：

1. 新增 `/api/plan/preview`：
   - 输入 map、slots、options。
   - 调 `sc2-composer plan`。
   - 返回 plan summary。
2. 新增 `/api/plan/launch`：
   - 输入 plan id。
   - 调 launcher 执行 plan。
3. Web 不直接写 Bank、不直接拼依赖。
4. Web 展示 plan 中的 validation 状态。

### 5.6 统一验证报告

问题：

- 现在验证结果分散在 logs、console、docs、低成本产物。

改进：

新增：

```text
out/verification/<compositionId>/<runId>.verification.json
out/verification/<compositionId>/<runId>.md
```

字段：

```json
{
  "schemaVersion": 1,
  "compositionId": "...",
  "runId": "...",
  "checks": {
    "schema": "pass",
    "datacenter": "pass",
    "dependencyClosure": "pass",
    "galaxyChecker": "pass",
    "documentRoundtrip": "pass",
    "runtimeSmoke": "pass",
    "unitDiagnostics": "partial",
    "bankIsolation": "pending"
  },
  "evidence": [],
  "failures": [],
  "incompleteReasons": []
}
```

### 5.7 将 root scripts 分级

问题：

- `scripts/` 根目录有大量历史脚本、临时脚本、启动脚本、构建脚本混在一起。

改进：

```text
scripts/
├─ sc2-composer/
├─ sc2-launcher/
├─ sc2-editor-toolkit/
├─ sc2-verify/
├─ builders/
├─ launchers/
├─ maintenance/
└─ legacy/
```

迁移规则：

- 正在使用的入口保留 wrapper，内部转发到新路径。
- 临时 `_*.py` 全部进入 `scripts/legacy/scratch/` 或删除。
- 任何保留脚本必须有 synopsis、输入、输出、是否写文件、验证命令。

### 5.8 建立系统状态页

问题：

- 现在需要读多份总结才能知道项目进度。

改进：

新增：

```text
docs/PROJECT_STATUS.md
```

内容：

- 当前主线目标。
- 当前可运行组合。
- 当前已验证组合。
- 当前高风险债务。
- 当前下一步任务。
- 最近一次验证报告路径。

该文件只放状态，不放长设计。

## 6. 推荐实施路线

### Phase 1：事实源防漂移

任务：

1. 给 `Shared/Launcher/*.json` 增加迁移目标说明。
2. 在 launcher config validation 中检查 CommanderPackage 冲突。
3. `LauncherCompatibilityPlan` 增加 `knownDebt`、`sourceDataCenter`、`sourceManifest`。
4. Reborn `-DryRun` 输出 plan + validation report。

完成标准：

- 同一 commander 在 launcher mapping 和 CommanderPackage 不一致时失败。
- plan 明确说明哪些字段来自临时配置。

## 9. 验收标准

本设计第一阶段完成时，应满足：

1. `docs/PROJECT_STATUS.md` 存在并能反映当前系统状态。
2. Reborn launcher plan 明确列出事实来源和已知债务。
3. Galaxy 注入有 manifest 初版。
4. `sc2-composer plan` 能生成 Reborn Raynor 的 CompositionPlan 或兼容 plan。
5. `zexpedition03 × TerranRaynor` 有统一验证报告。
6. Web/PowerShell/CLI 至少有一个入口能消费同一 plan。
7. 新增失败模式会进入 schema、fixture、linter 或低成本任务包，而不是只写经验总结。

## 10. 总结

当前项目不是缺脚本，而是脚本、配置、文档和验证各自发展太快，已经需要一条更强的系统总线。

下一阶段最重要的不是继续增加启动器能力，而是：

```text
把事实收敛到 manifest/profile/package/datacenter
把计划收敛到 CompositionPlan
把执行收敛到 plan runner
把验证收敛到 VerificationReport
把批量低智任务收敛到标准任务包
```

做到这一步后，后续“任意指挥官 × 任意地图”才会从一次次手工搬运，变成可以迭代、可以验证、可以下放的工程流水线。
