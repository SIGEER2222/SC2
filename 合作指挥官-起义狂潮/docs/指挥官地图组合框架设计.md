# 指挥官与地图组合框架设计

> 状态：架构设计草案
> 日期：2026-07-11
> 最终目标：任意已接入指挥官可以进入任意已接入地图游玩
> 首个非 7vs1 试点：重生虫心 `zexpedition03`

## 1. 目标定义

本项目的最终产物不是若干张“修到能启动”的地图，而是一套可持续扩展的组合平台：

```text
已接入地图集合 × 已接入指挥官集合
             ↓
       CompositionPlan
             ↓
  可复现的依赖、代码、地图补丁和启动产物
```

用户选择：

- 地图。
- 一个或多个指挥官。
- 每个玩家槽位对应的指挥官。
- 威望、精通、天赋、通用加成等运行时选项。

系统负责：

- 解析地图和指挥官能力。
- 计算有序依赖。
- 识别 Catalog、Galaxy、UI、玩家槽位和 Bank 冲突。
- 选择地图适配器、指挥官适配器和必要的组合补丁。
- 生成组合专用 bootstrap 和地图工作副本。
- 执行静态验证、启动、运行时探针和回归记录。

这里的“任意”定义为：

- 新地图接入后，默认可与所有已接入指挥官组合。
- 新指挥官接入后，默认可与所有已接入地图组合。
- 暂时无法组合的情况必须有显式、可测试、可追踪的 incompatibility 记录。
- 不允许通过“缺少映射”“静默忽略依赖”或“启动后看运气”表达不兼容。

## 2. 当前系统为什么还不能实现该目标

### 2.1 配置模型仍是单层 profile

当前 `Shared/Workflow/sc2-workflow.json` 的核心结构是：

```text
effectiveProfile
  -> targetPattern
  -> alwaysDependencies
  -> commanderDependencies
```

具体实现由地图文件名正则选择第一个 profile：

- `scripts/sc2-editor-toolkit/src/dependencyGraph.mjs:120-128`

指挥官依赖嵌套在地图 profile 内：

- `scripts/sc2-editor-toolkit/src/dependencyGraph.mjs:135-139`

这意味着：

- CommanderProfile 不是独立实体，不能被多个 MapProfile 复用。
- 同一地图不能显式选择不同宿主策略。
- 未指定指挥官时会展开 profile 中的所有指挥官。
- 未知指挥官会静默得到空依赖。
- 多个 profile 同时命中时没有冲突检查。
- 依赖数组只有顺序，没有依赖层、插入槽和所有权语义。

当前工作区中的 `reborn-integrated` 草稿还造成了 JSON 语法错误，真实配置无法解析。这说明配置 schema 和真实配置测试尚未成为硬门禁。

### 2.2 三套入口维护三份事实

当前组合事实分散在：

- `Shared/Workflow/sc2-workflow.json`
- `scripts/launch-7vs1-coop-test.ps1`
- `web-launcher/maps.json`
- `web-launcher/services/launch-args-builder.mjs`
- `web-launcher/lib/maps-loader.mjs`

现状包括：

- PowerShell 启动器硬编码 commander 到 `CommanderUnits_*` 的映射：
  - `scripts/launch-7vs1-coop-test.ps1:111-140`
- 启动器再次硬编码公共依赖和全量指挥官列表：
  - `scripts/launch-7vs1-coop-test.ps1:146-189`
- Web 地图发现只认识 `_7vs1` 和 `_xm`：
  - `web-launcher/lib/maps-loader.mjs:32-67`
- Web 参数构造只区分 XM 与 7vs1：
  - `web-launcher/services/launch-args-builder.mjs:218-230`
- 场景参数校验失败时会退化为直接 Switcher：
  - `web-launcher/routes/scenario.mjs:56-69`

因此 toolkit、CLI、Web 和启动器可能对同一组合计算出不同结果。

### 2.3 CoreRuntime 仍编译期知道全部指挥官

当前目录已经拆出 `CommanderUnits_*`，但运行时没有真正解耦：

- `CoreRuntime` 主库直接 include 指挥官 Runtime、注册表、StartSquad 和全部 Adapter。
- `LibE0EAE146_h.galaxy` 暴露大量具体指挥官函数。
- `CommanderRegistry` 仍生成逐指挥官分支和直接函数调用。
- `AdapterBootstrap` 编译期初始化全部 Adapter。
- 启动器为满足 include，又把全部 CommanderUnits 和 Adapter Galaxy 注入编译环境。

相关证据：

- `Mods/7vs1/CoreRuntime.SC2Mod/Base.SC2Data/LibE0EAE146.galaxy:16-54`
- `Mods/7vs1/CoreRuntime.SC2Mod/Base.SC2Data/LibE0EAE146_h.galaxy:176-205`
- `Mods/7vs1/CoreRuntime.SC2Mod/Base.SC2Data/LibE0EAE146_h.galaxy:277-309`
- `Mods/7vs1/CoreRuntime.SC2Mod/Base.SC2Data/LibE0EAE146_CommanderRegistry.galaxy:105-191`
- `Mods/7vs1/CoreRuntime.SC2Mod/Base.SC2Data/LibE0EAE146_AdapterBootstrap.galaxy:5-49`
- `scripts/launch-7vs1-coop-test.ps1:1312-1354`

结果是：

- 每新增一个指挥官都可能修改 CoreRuntime。
- 每新增一个地图族都可能向 CoreRuntime 增加条件。
- Adapter 容易变成指挥官数据的第二所有者。
- 组合数量增加后，条件分支和交叉引用呈乘法增长。

### 2.4 7vs1 启动器不是通用地图适配器

`launch-7vs1-coop-test.ps1` 会：

- 删除地图 `Base.SC2Data/Lib*.galaxy` 后复制运行时库：
  - `scripts/launch-7vs1-coop-test.ps1:431-458`
- 重写 DocumentInfo 和 DocumentHeader：
  - `scripts/launch-7vs1-coop-test.ps1:519-674`
- 重建依赖列表：
  - `scripts/launch-7vs1-coop-test.ps1:1243-1297`
- 注入 CommanderBridge、CommanderUnits、Adapter 和其他 Galaxy：
  - `scripts/launch-7vs1-coop-test.ps1:1308-1354`

该方式能服务已经按 7vs1 结构设计的地图，但会破坏普通战役地图自己的 Galaxy 边界，不能成为任意地图的默认组合机制。

## 3. 架构原则

### 3.1 两个独立领域

系统必须把问题拆成两个独立领域：

**地图领域**

- 任务目标。
- 敌人和 AI。
- 盟友、玩家槽位和联盟。
- 任务资源和任务科技。
- 剧情角色、过场和原生 UI。
- 胜利与失败。
- 剧情 Bank 和战役进度。
- 地图初始化生命周期。

**指挥官领域**

- 指挥官 Catalog。
- 生产建筑、单位、技能、升级和科技树。
- 英雄、复活、英雄建筑。
- 顶栏和全局施法单位。
- 起始单位。
- 威望、精通、天赋和通用加成。
- 指挥官自己的 Bank 命名空间。

两个领域只能通过稳定契约组合。

### 3.2 单一所有者

每个行为和数据必须有一个 canonical owner：

- 地图任务语义归地图。
- 指挥官单位和能力归 CommanderPackage。
- 通用服务归 PlatformKernel 或 CapabilityPackage。
- 地图与指挥官差异归 Adapter 或 PairPatch。
- 依赖计算和代码生成归 CompositionCompiler。

禁止同一 Catalog ID 在多个 CommanderPackage 中同时作为 canonical 定义。

### 3.3 默认组合，显式例外

- 兼容是默认状态。
- 不兼容必须写入规则文件并说明缺少的 capability 或无法解决的冲突。
- 未声明、未知或不完整状态必须失败，不能静默降级。
- “还没验证”与“明确不兼容”是两种不同状态。

### 3.4 生成组合，不做全量聚合

Galaxy 的静态 include 和函数解析限制意味着运行时完全动态插件化并不现实。

因此采用：

- 元数据和 schema 描述包。
- 构建时选择地图和指挥官。
- 生成只包含当前组合的 dispatcher/bootstrap。
- 不让 CoreRuntime include 所有指挥官。
- 不让启动器注入全仓库 Galaxy 文件。

### 3.5 原图不可变

- 原始地图和原始 Mod 只读。
- 所有依赖改写、hook 和地图本地补丁作用于生成副本。
- 生成产物必须由 source hash + profile + patch manifest 重建。

## 4. 核心概念

### 4.1 PlatformKernel

稳定、地图无关、指挥官无关的最小内核。

保留：

- 玩家与指挥官身份。
- 生命周期状态。
- 通用 hook 调度。
- Catalog 查询与安全修改封装。
- Bank 命名空间访问封装。
- 日志、断言、错误和运行时探针。
- 通用 capability 注册与查询。

不保留：

- 具体指挥官 ID。
- 具体地图 ID。
- 某个地图族的玩家组。
- 指挥官单位、技能、StartSquad 列表。
- 某个指挥官的复活单位和英雄建筑。
- 7vs1、XM、Reborn 专用 Bank 键。

建议目标包：

```text
Mods/Platform/PlatformKernel.SC2Mod
```

### 4.2 CapabilityPackage

可被多个指挥官复用的通用机制：

- HeroRevive。
- HeroStructure。
- TopPanel。
- SOATargeting。
- TalentEngine。
- CommanderPower。
- GenericBonus。
- RuntimeProbe。

CapabilityPackage 只能实现机制，不能硬编码指挥官内容。

示例：

```text
Mods/Platform/Capabilities/HeroRevive.SC2Mod
Mods/Platform/Capabilities/TopPanel.SC2Mod
```

### 4.3 CommanderPackage

一个可独立选择的指挥官实现。

建议每个指挥官由一个清单描述，实际 Catalog 和 Runtime 可以先保留为一个 Mod，后续再按必要性拆分：

```text
Mods/Commanders/Raynor/Raynor.SC2Mod
Shared/Commanders/TerranRaynor.json
```

清单契约：

```yaml
identity:
  id: TerranRaynor
  aliases: [Raynor]
  race: Terran
  version: 1

dependencies:
  requiredBaseMods: []
  requiredCapabilities: [top-panel, hero-revive]

catalog:
  ownedIds: []
  extendedIds: []
  localizationRoots: []

runtime:
  init: RaynorRuntime_Init
  applyTech: RaynorRuntime_ApplyTech
  createStartSquad: RaynorRuntime_CreateStartSquad
  createCargoSquad: RaynorRuntime_CreateCargoSquad
  initUi: RaynorRuntime_InitUi

metadata:
  heroUnit: ""
  heroStructure: ""
  primaryTownHalls: []
  reviveUnit: ""
  consoleSkin: ""
  topPanelCaster: ""

requirements:
  mapCapabilities: []

validation:
  expectedProducers: []
  expectedUnits: []
  expectedAbilities: []
  runtimeProbes: []
```

CommanderPackage 不得：

- 引用地图点、区域、任务触发器或具体地图 ID。
- 读写剧情 Bank。
- 修改其他玩家的科技树。
- 定义另一个指挥官的 canonical 数据。
- 依赖某个 MapAdapter。

### 4.4 MapProfile

MapProfile 是地图的机器可读契约，不包含实现代码。

建议位置：

```text
Shared/Maps/profiles.schema.json
Shared/Maps/profiles/<family>/<map-id>.json
```

示例：


MapProfile 必须声明：

- 可用指挥官槽位。
- 地图保留槽位。
- 地图所有权。
- 生命周期 hook。
- Bank 边界。
- 资源和科技合并策略。
- UI 保留区域。
- 地图提供和缺失的 capabilities。

### 4.5 MapAdapter

MapAdapter 把统一生命周期映射到具体地图族。

建议 API：

```text
MapAdapter_ProfileId() -> string
MapAdapter_CommanderPlayers() -> playergroup
MapAdapter_MissionAllies() -> playergroup
MapAdapter_MissionEnemies() -> playergroup
MapAdapter_CommanderSpawnPoint(player) -> point
MapAdapter_OnAfterTechnologyInit()
MapAdapter_OnAfterPlayersInit()
MapAdapter_OnAfterUnitsInit()
MapAdapter_OnBeforeIntro()
MapAdapter_OnMissionVictoryObserved()
MapAdapter_OnMissionDefeatObserved()
MapAdapter_CanAccessStoryBank(name) -> bool
```

职责：

- 提供精确的玩家组和出生上下文。
- 在地图自己的初始化完成后调用 Commander Runtime。
- 按 profile 合并资源和科技。
- 旁听胜负用于保存指挥官统计，但不改变任务结果。
- 保护地图剧情 Bank。

不得：

- 重写地图目标、AI 或剧情。
- 定义指挥官单位和技能。
- 对所有人类玩家无差别解锁科技。
- 直接 include 某个具体 CommanderPackage。

### 4.6 CommanderAdapter

CommanderAdapter 处理某个 CommanderPackage 在某种宿主环境中的差异。

示例：

```yaml
identity:
  commanderPackage: TerranTychus
  hostProfile: generic-campaign
  version: 1

compatibility:
  requiredHostCapabilities: [top-panel-slot]
  supportedMapFamilies: [7vs1, reborn]

translations:
  commanderAliases: {}
  catalogIdAliases: {}
  eventMappings: {}

hooks:
  beforeHostInit: ""
  afterHostInit: ""
  afterTechReset: ""
  mapStart: ""

overrides: []
conflicts: []
```

Adapter 只描述差异，不得成为指挥官数据的第二所有者。

### 4.7 PairPatch

PairPatch 是特定地图或地图族与特定指挥官之间的最后例外。

只允许用于：

- 地图本地同 ID 数据最终覆盖了指挥官必须字段。
- 地图科技 reset 无法通过通用 hook 恢复。
- 地图 UI 与某指挥官 UI 存在无法通用解决的冲突。
- 地图使用固定英雄或生产链，需要显式翻译。

PairPatch 应是声明式 patch manifest：

```text
Shared/Compatibility/<map-family>/<commander-id>.json
```

不能把 PairPatch 逻辑重新塞回 PlatformKernel。

### 4.8 CompositionPlan

CompositionPlan 是所有工具消费的单一真源。

输入：

- MapProfile。
- 每个 commander slot 的 CommanderPackage。
- CommanderAdapter。
- PairPatch。
- 平台版本。
- 用户威望、精通和天赋选项。

输出：

- 完整有序依赖。
- 所需文件和哈希。
- capability 匹配结果。
- Catalog 冲突决策。
- 生成的 Galaxy bootstrap。
- 地图本地 patch。
- 静态验证任务。
- 启动命令和运行时 probe。

示例：

```json
{
  "schemaVersion": 1,
  "compositionId": "reborn.zexpedition03__p1-TerranRaynor",
  "mapProfile": "reborn.zexpedition03",
  "slots": {
    "1": {
      "commander": "TerranRaynor",
      "adapter": "TerranRaynor@generic-campaign"
    }
  },
  "dependencyLayers": [],
  "capabilities": {},
  "catalogDecisions": [],
  "localPatches": [],
  "generatedBootstrap": "",
  "validation": {}
}
```

## 5. 依赖与代码生成

### 5.1 依赖层

CompositionCompiler 按明确层次生成依赖：

```text
L0 官方 Base / Campaign
L1 地图原始依赖和地图族资源包
L2 PlatformKernel
L3 通用 CapabilityPackage
L4 当前选中的 CommanderPackage
L5 MapAdapter
L6 CommanderAdapter
L7 可作为依赖表达的 PairPatch
L8 地图本地 GameData、Triggers 和生成 bootstrap
```

必须记录每个条目的层、来源和原因。

禁止：

- 依赖列表中出现未声明的隐式复制。
- 同一依赖重复出现。
- 未选择的指挥官包进入组合。
- 启动器扫描整个目录后注入全部 Galaxy。
- 用数组位置暗示层次但不声明语义。

### 5.2 地图本地数据始终最后

SC2 地图本地数据在依赖之后生效，因此某些冲突不能靠更晚的公共 Mod 修复。

处理顺序：

1. 优先保留地图语义。
2. 能通过继承或有序依赖解决的，放依赖层。
3. 能在生命周期 hook 后安全恢复的，使用 runtime overlay。
4. 必须覆盖地图本地字段的，写入生成地图的 local patch。
5. 每个 local patch 必须有字段级原因和回归测试。

### 5.3 生成组合 bootstrap

Galaxy 缺少通用动态模块加载，因此为每个组合生成最小 bootstrap：

```text
Base.SC2Data/
  LibCOMPOSITION_<hash>_h.galaxy
  LibCOMPOSITION_<hash>.galaxy
```

职责：

- 注册选中的玩家和指挥官。
- 只调用选中的 CommanderPackage。
- 只初始化选中的 Adapter。
- 把 MapAdapter hook 转发到 Commander Runtime。
- 暴露运行时探针。

禁止在 PlatformKernel 中生成全量 commander switch。

## 6. 生命周期协议

### 6.1 统一阶段

```text
CompositionRegistered
MapTechnologyReady
MapPlayersReady
MapUnitsReady
CommanderTechApplied
CommanderStartCreated
CommanderUiReady
MapIntroReady
MissionRunning
MissionVictoryObserved
MissionDefeatObserved
```

### 6.2 地图初始化顺序

不能依赖多个 MapInit trigger 的隐式执行顺序。

地图适配应插入小型显式 hook：

1. 地图完成任务科技后：
   - `MapTechnologyReady`
   - 只叠加选中指挥官科技。
   - 不清除地图任务科技。
2. 地图完成玩家、联盟和初始资源后：
   - `MapPlayersReady`
   - 注册 commander slots。
   - 按 `preserve/add/set` 策略处理指挥官资源。
3. 地图完成原生单位创建后：
   - `MapUnitsReady`
   - 创建指挥官起始单位和英雄。
   - 避免被地图初始化覆盖或删除。
4. 地图准备播放开场前：
   - 初始化不会破坏剧情 UI 的指挥官 UI。
5. 地图执行原生胜负前：
   - Runtime 只能旁听和保存自己的统计。
   - 最终胜负仍由地图决定。

### 6.3 精确玩家范围

- MapAdapter 必须显式传入 commander playergroup。
- CommanderPackage 只能修改自己的 player。
- 禁止 `PlayerGroupAll()` 或“所有人类玩家”作为普通 Adapter 的默认范围。
- 多指挥官地图按 slot 独立初始化，不能假设所有玩家使用同一指挥官。

## 7. 所有权矩阵

| 能力 | Map | MapProfile | MapAdapter | Platform | CommanderPackage | PairPatch |
| --- | --- | --- | --- | --- | --- | --- |
| 任务目标/AI | 拥有 | 声明 | 不改 | 不知情 | 不知情 | 极少例外 |
| 胜负 | 拥有 | 声明 | 旁听 | 提供事件 | 不决定 | 禁止替换 |
| 玩家槽位 | 原始定义 | 拥有契约 | 映射 | 接收注册 | 使用自己的槽位 | 可修映射 |
| 联盟 | 拥有 | 声明 | 读取 | 不改 | 不改 | 极少例外 |
| 任务科技 | 拥有 | 声明 | 保护 | 提供封装 | 不清除 | 可恢复 |
| 指挥官科技 | 不拥有 | 声明合并策略 | 调度 | 安全应用 | 拥有 | 可补偿 |
| 任务资源 | 拥有 | 声明 | 保护 | 不改 | 不改 | 禁止覆盖 |
| 指挥官起始资源 | 不拥有 | 声明策略 | 合并 | 提供 API | 声明需求 | 可补偿 |
| 剧情 Bank | 拥有 | 白名单 | 默认拒绝 | 命名空间隔离 | 禁止访问 | 禁止访问 |
| 指挥官 Bank | 不访问 | 声明命名空间 | 不解释 | 提供 API | 拥有 | 不拥有 |
| 指挥官 Catalog | 不拥有 | 冲突策略 | 不定义 | 查询/校验 | 拥有 | 只修组合差异 |
| 指挥官 UI | 保留地图区域 | 声明 UI 能力 | 分配/避让 | 通用控制器 | 拥有内容 | 可修冲突 |

## 9. Bank 与进度隔离

Bank 分三类：

```text
map-owned
platform-owned
commander-owned
```

规则：

- MapAdapter 默认不能读写 map-owned Bank。
- Platform 只访问自己的命名空间。
- CommanderPackage 只访问自己的命名空间或 Platform 提供的 Commander API。
- PairPatch 不能迁移或覆盖剧情 Bank。
- 任意 Bank 访问都必须能追踪到 owner。

Reborn 的 `cryswarmcoop`、`ZCampaign*`、`ZStory*`、`ZArmy`、`TCampaign` 等属于地图/战役所有。

## 10. UI 组合

顶栏、英雄面板、任务 UI 和剧情 UI 是独立冲突面。

MapProfile 声明：

- 地图保留的 UI 区域。
- 可用顶栏 slot。
- 是否允许全局施法面板。
- 是否存在原生英雄面板。
- 过场时需要隐藏的 commander UI。

CommanderPackage 声明：

- 必需 UI capabilities。
- 可降级 UI。
- caster 数量。
- 面板资源和事件。

CompositionCompiler 负责：

- capability 匹配。
- 选择通用 UI controller。
- 生成当前组合的 UI 注册。
- 冲突时选择明确的 fallback 或标记不兼容。

## 13. 全组合验证策略

### 13.1 静态全矩阵

对每个：

```text

```

生成 CompositionPlan，并验证：

- 依赖顺序稳定。
- 无 legacy 依赖。
- 无重复依赖。
- 无 unresolved。
- capability 匹配。
- Catalog owner 唯一。
- PairPatch 可解析。
- Galaxy checker 无可修复错误。

静态全矩阵是低成本任务，适合交给低成本模型或本地批处理执行。

### 13.2 运行时等价类

## 18. ADR

### 决策

采用“独立领域包 + MapAdapter + CommanderAdapter + 组合代码生成”的架构。

### 驱动因素

- 地图和指挥官组合数量将持续增长。
- SC2 依赖和地图本地数据存在覆盖顺序。
- Galaxy 静态 include 限制完全动态插件化。
- 战役地图拥有不可替代的任务、剧情和 Bank 语义。
- 当前 CoreRuntime 和启动器的全量聚合方式无法长期维护。

### 考虑过的替代方案

**继续扩展 CoreRuntime**

- 初期改动少。
- 组合增长后条件分支、include 和回归范围失控。
- 否决。

**每张地图复制一套指挥官运行时**

- 单图容易跑通。
- 无法复用，无法统一修复，长期产生大量分叉。
- 否决。

**完全运行时动态插件**

- 理论解耦最好。
- Galaxy 的静态符号和 include 限制使实现成本和风险过高。
- 否决。

**构建时生成当前组合**

- 可以保持运行时最小化。
- 能精确控制依赖、符号和补丁。
- 支持可复现验证。
- 采用。

### 后果

- 前期需要建设 schema、CompositionCompiler 和迁移工具。
- 短期内新旧运行时需要并存。
- 地图本地覆盖仍要求生成 local patch。
- 以后新增地图或指挥官的边际成本显著下降。

### 后续动作

1. 修复并验证当前 workflow 配置。
2. 建立 CompositionPlan schema 和真实配置测试。
3. 用现有 7vs1 组合复现依赖输出。
4. 标准化 Raynor CommanderPackage。
5. 建立 Reborn `zexpedition03` MapProfile 和三个显式 hook。

## 19. 与重生虫心搬运方案的关系

`重生虫心地图搬运设计.md` 不再是独立的一次性方案，而是本架构的第一个 MapFamily 实施计划：

```text
Reborn 原始地图和五 Mod
  -> Reborn MapProfile
  -> RebornMapAdapter
  -> 选中的 CommanderPackage
  -> 组合 bootstrap
  -> 必要的 PairPatch
  -> 生成地图
```

`RebornBridge` 应逐步收敛为 `RebornMapAdapter`：

- 不拥有指挥官 canonical 数据。
- 不复制整套 CoreRuntime。
- 不改剧情 Bank 和任务胜负。
- 只提供 Reborn 生命周期、槽位和所有权适配。

重生虫心试点的价值不是只搬完 30 张图，而是证明该组合框架可以脱离 7vs1 地图运行。
