# Mod 与地图开发规范及现有改造计划

> 状态：可执行规范 v1  
> 日期：2026-07-11  
> 范围：`合作指挥官-起义狂潮`  
> 目标：把 Mod、地图、数据中心、Galaxy、启动器和验证流程收敛成可长期维护的开发规范，并给出现有项目的具体改造计划。

## 1. 背景与目标

当前项目的长期目标是：

```text
任意已接入指挥官 × 任意已接入地图
        ↓
可复现 CompositionPlan
        ↓
明确依赖、明确 owner、明确补丁、明确验证证据
```

这个目标不能继续依赖“哪个地图能跑就复制哪些依赖”“缺什么就往启动器里补”“全量注入全部 Galaxy 文件”这类手工策略。SC2 的核心约束是：

- 依赖项是父级数据模型，地图和后加载包只能继承、合并或覆盖父依赖。
- 同 ID Catalog 在不同依赖层出现时，最终有效字段由加载顺序、继承、数组合并和地图本地数据共同决定。
- 地图本地数据在依赖之后生效，很多冲突不能靠再追加一个公共 Mod 解决。
- Galaxy 是静态 include 和静态符号模型，不能假设运行时可以动态插件化。
- 自定义对战能跑通，不代表战役地图能跑通；战役图有自己的科技 reset、剧情 Bank、玩家槽位、任务触发器和地图本地覆盖。

因此本规范的目标是：

1. 明确 Mod、地图、数据中心和适配层的职责边界。
2. 规定新增地图和新增指挥官的接入流程。
3. 规定 Catalog、Galaxy、UI、Bank、触发器和本地化的安全开发规则。
4. 把低判断、高 token 的任务沉淀为本地任务包或工具。
5. 给出现有项目从当前状态迁移到目标结构的分阶段计划。

## 2. 总体架构规范

### 2.1 标准分层

目标分层如下：

```text
L0 官方基础依赖
  Liberty / Swarm / Void / StarCoop / Campaign 官方依赖

L1 原地图依赖
  原图声明的依赖，不主动删除，先做审计

L2 PlatformKernel
  通用运行时、日志、断言、Catalog 安全封装、Bank 命名空间、生命周期总线、运行时探针

L3 CapabilityPackage
  HeroRevive、TopPanel、TalentEngine、RuntimeProbe 等可复用机制

L4 CommanderPackage / CommanderDataCenter
  单个指挥官的 canonical Catalog、Galaxy runtime、起始单位、科技、UI 元数据

L5 MapFamilyDataCenter
  地图族共享补丁，例如 RebornHotS、7vs1、XM

L6 MapAdapter / CommanderAdapter
  生命周期、玩家槽位、地图族差异、指挥官在宿主环境中的差异

L7 PairPatchDataCenter
  特定地图族 × 特定指挥官的少量例外

L8 生成地图本地 patch / generated bootstrap
  当前组合专属、可重建、可验证的最后覆盖层
```

任何新功能必须先判断自己属于哪一层。无法判断 owner 的改动不得直接落入共享包。

### 2.2 单一真源

四类 manifest 是长期单一真源：

| Manifest | 职责 |
| --- | --- |
| `CompositionPlan` | 一个地图与一个或多个指挥官组合后的完整依赖、Galaxy、补丁和验证计划 |
| `DataCenter.json` | 一个数据中心拥有的 Catalog/Galaxy/本地化/导出资源 |
| `MapProfile` | 一个地图或地图族的玩家槽位、生命周期、Bank、UI 和所有权契约 |
| `CommanderPackage` | 一个指挥官的身份、能力、依赖、生产链、runtime 和验证契约 |

禁止 CLI、Web、PowerShell 启动器、toolkit 各自维护不同 commander/map 映射。过渡期存在重复映射时，必须在状态页标成 compatibility shim，并设置移除条件。

### 2.3 原始地图和原始 Mod 只读

规范：

- 原始地图、原始第三方 Mod、原始战役依赖只读保存。
- 所有改写发生在生成副本、适配层或项目自有数据中心。
- 每个生成产物必须能由 source hash + CompositionPlan + patch manifest 重建。
- 不允许把一次性修出来的地图当作新的事实源继续手工编辑。

## 3. Mod 开发规范

### 3.1 Mod 类型

| 类型 | 目标位置 | 允许内容 | 禁止内容 |
| --- | --- | --- | --- |
| `PlatformKernel` | `Mods/Platform/PlatformKernel.SC2Mod` | 生命周期总线、日志、Bank API、Catalog 安全封装、探针 | 具体指挥官、具体地图族、全量 commander switch |
| `CapabilityPackage` | `Mods/Platform/Capabilities/<Capability>.SC2Mod` | 通用机制 | 具体地图逻辑、具体指挥官 canonical 数据 |
| `CommanderDataCenter` | `Mods/Commanders/<Commander>/<Commander>.SC2Mod` | 单指挥官单位、技能、升级、Actor、runtime | 地图点、区域、任务触发器、剧情 Bank |
| `MapFamilyDataCenter` | `Mods/MapFamilies/<Family>/<Family>Data.SC2Mod` | 地图族共享桥接数据 | 指挥官 canonical 数据、地图胜负/剧情重写 |
| `MapAdapter` | `Mods/MapFamilies/<Family>/<Family>Adapter.SC2Mod` | hook、玩家槽位、生命周期映射 | 指挥官单位定义、全玩家科技解锁 |
| `PairPatchDataCenter` | `Mods/Compatibility/<Family>_<Commander>.SC2Mod` | 特定组合的少量字段修正 | 长期通用逻辑、无原因的大补丁 |

### 3.2 Mod 命名

目录、文件、内部 ID 尽量使用 ASCII。中文只用于显示文本、本地化文案和文档。

推荐命名：

```text
PlatformKernel.SC2Mod
TopPanel.SC2Mod
RuntimeProbe.SC2Mod
TerranRaynor.SC2Mod
RebornHotSData.SC2Mod
RebornHotSAdapter.SC2Mod
RebornHotS_TerranRaynor.SC2Mod
```

避免命名：

```text
新建模组.SC2Mod
测试.SC2Mod
通用补丁.SC2Mod
Unit.xml
Actor.xml
```

### 3.3 Catalog ID 规范

新增 ID 推荐前缀：

| 层 | 前缀 |
| --- | --- |
| Platform | `PX_` |
| Capability | `PXTopPanel_`、`PXHeroRevive_` |
| Commander 新增数据 | `CMRaynor_`、`CMAbathur_` |
| MapFamily | `MFReborn_`、`MF7v1_` |
| PairPatch | `PPRebornRaynor_` |
| Test/Fixture | `TestHalo_`、`Fixture_` |

已有官方或第三方 ID 不强制改名，但必须在 owner manifest 中声明：

```json
{
  "catalog": {
    "ownedIds": ["BarracksRaynor", "MarineRaynor"],
    "extendedIds": ["Marine", "Marauder"],
    "externalIds": ["cryswarmcoop_*"]
  }
}
```

规则：

- 新增系统优先新增唯一 ID，不覆盖官方或地图本地 ID。
- 必须覆盖同 ID 时，写明原因、字段路径、来源和验证方式。
- 同一 canonical Catalog ID 只能有一个 owner。
- PairPatch 只能修组合差异，不能成为第二 owner。

### 3.4 数据空间规范

每个长期维护的 SC2Mod 应逐步使用 `GameData.xml <Includes>` 管理数据空间：

```text
Base.SC2Data/
├─ GameData.xml
└─ GameData/
   ├─ RaynorUnits.xml
   ├─ RaynorAbilities.xml
   ├─ RaynorButtons.xml
   ├─ RaynorActors.xml
   ├─ RaynorEffects.xml
   ├─ RaynorBehaviors.xml
   ├─ RaynorUpgrades.xml
   └─ RaynorRequirements.xml
```

`GameData.xml` 示例：

```xml
<?xml version="1.0" encoding="utf-8"?>
<Includes>
    <Catalog path="GameData/RaynorUnits.xml"/>
    <Catalog path="GameData/RaynorAbilities.xml"/>
    <Catalog path="GameData/RaynorButtons.xml"/>
    <Catalog path="GameData/RaynorActors.xml"/>
    <Catalog path="GameData/RaynorEffects.xml"/>
    <Catalog path="GameData/RaynorBehaviors.xml"/>
    <Catalog path="GameData/RaynorUpgrades.xml"/>
    <Catalog path="GameData/RaynorRequirements.xml"/>
</Includes>
```

规则：

- 文件名 ASCII。
- XML 内容 UTF-8。
- 一个数据空间只服务一个清晰主题。
- 数据空间拆分只改变组织方式，不改变行为。
- 迁移后必须 trace 关键 Catalog ID，确认没有丢失。
- 同一 Mod 内不要长期混用 `<Includes>` 和未登记的默认自动加载 XML。

### 3.5 DataCenter.json 必须随 Mod 存在

长期数据中心必须有：

```text
DataCenter.json
Base.SC2Data/GameData.xml
Base.SC2Data/GameData/*.xml
```

最小字段：

```json
{
  "schemaVersion": 1,
  "id": "Commander.TerranRaynor",
  "type": "CommanderDataCenter",
  "owner": "TerranRaynor",
  "gameDataEntry": "Base.SC2Data/GameData.xml",
  "spaces": [],
  "exports": {},
  "imports": {},
  "galaxyRuntime": {}
}
```

完成标准：

- `spaces` 中每个路径存在。
- `catalogIds` 可由 linter 填充或验证。
- `exports` 与 CommanderPackage 的 expected producers/units/abilities 对齐。
- `galaxyRuntime` 声明主 runtime 文件和 init 函数。

## 4. 地图开发规范

### 4.1 MapProfile 是地图契约

每个接入地图必须有 MapProfile：

```text
Shared/Maps/profiles/<family>/<map-id>.json
```

必须声明：

- 地图 ID、family、source。
- 原始依赖是否保留。
- commander slots。
- mission allies/enemies/neutral slots。
- 地图所有权：胜负、AI、任务科技、资源、剧情 Bank、UI。
- 生命周期 hook：technologyReady、playersReady、unitsReady、introReady、victoryObserved、defeatObserved。
- mutationPolicy：Catalog 修改范围、未知条目策略、地图科技保护策略。

地图接入不是“能启动”，而是把地图边界写成机器可读契约。

### 4.2 地图本地数据最小化

地图本地允许：

- 任务目标。
- 地图专属单位和剧情单位。
- 地图 AI、触发器、区域和点。
- 地图剧情 UI 和胜负逻辑。
- 必须最终覆盖的 generated local patch。

地图本地不允许长期承载：

- 指挥官 canonical 单位。
- 指挥官通用技能、按钮、升级和 Actor。
- 通用运行时库。
- 所有地图都需要的 Platform 数据。
- 其他地图族复用的数据。

### 4.3 MapAdapter 只做适配

MapAdapter 职责：

- 显式返回 commander playergroup。
- 显式返回任务盟友、敌人、中立槽位。
- 在地图初始化完成后调用 Commander Runtime。
- 合并资源和科技时遵守 MapProfile。
- 旁听胜负和保存指挥官统计。
- 保护剧情 Bank。

MapAdapter 禁止：

- 直接 include 某个具体 CommanderPackage。
- 批量修改所有人类玩家科技。
- 重写任务目标、AI 或剧情。
- 把指挥官单位定义塞进地图族包。

### 4.4 战役地图特殊规则

战役图优先级高于自定义对战图：

- 自定义对战通过不代表战役通过。
- 战役图常有地图本地科技 reset，需要在地图科技完成后再叠加指挥官科技。
- 战役图剧情 Bank 默认归地图所有，Adapter 默认拒绝访问。
- 战役图常有固定玩家槽位，不能用“所有人类玩家”作为默认范围。
- 战役图开场过场、剧情 UI 和任务目标 UI 必须作为 UI 冲突面处理。

## 5. Galaxy 开发规范

### 5.1 文件组织

Galaxy 头文件推荐顺序：

```text
include natives
preset / const
struct
global variables
function declarations
trigger declarations
InitVariables declaration
```

主库推荐结构：

```text
constants
state
public API
internal helpers
lifecycle hooks
trigger callbacks
InitVariables
```

### 5.2 幂等初始化

每个库都必须有幂等初始化守卫：

```galaxy
bool gv_initCompleted = false;

void InitVariables() {
    if (gv_initCompleted) {
        return;
    }
    gv_initCompleted = true;
}
```

原因：

- SC2 触发器库可能被多次 include 或初始化。
- 重复初始化会清空数组、重建触发器、重复注册事件。
- 对组合平台来说，重复初始化会放大成跨地图随机错误。

### 5.3 组合 bootstrap

长期目标是生成每个组合专属 bootstrap：

```galaxy
include "LibPLATFORM"
include "LibE0EAE146_RaynorRuntime"
include "LibRebornMapAdapter"

void LibCOMPOSITION_Init() {
    LibPLATFORM_Init();
    libE0EAE146_gf_RaynorRuntime_Init();
    libRebornMapAdapter_gf_Init();
}
```

规范：

- PlatformKernel 不 include 全部指挥官。
- CompositionCompiler 只 include 当前组合需要的 runtime。
- 启动器不得扫描目录后注入全部 Galaxy。
- 未选中的指挥官 runtime 不得进入当前组合。

### 5.4 Galaxy checker 门禁

修改 `.galaxy` 或 `_h.galaxy` 后必须：

1. 运行完整 galaxy-checker。
2. 如果出现运行时 ScriptError 而 checker 未报，先补 checker 规则或 fixture。
3. 再做游戏内验证。

常见规则：

- 本地变量声明不带初始化，初始化拆到下一行。
- 文本拼接显式转换，避免 `text + string`。
- 避免不被 xlib 允许的 native。
- `continue` 改成等价控制流。
- 内部 ID、变量名、函数名使用 ASCII。

## 6. UI 开发规范

### 6.1 UI 模块化

参考 Archipelago 的 `DescIndex + Include` 模式：

```xml
<Include path="UI/Layout/PXTopPanel.SC2Layout"/>
<Include path="UI/Layout/PXRuntimeProbe.SC2Layout"/>
```

规则：

- 每个面板独立 layout 文件。
- DescIndex 只做入口，不堆业务细节。
- Platform 提供通用模板，Commander 只注册内容。
- MapProfile 声明地图保留 UI 区域。
- CompositionPlan 决定 UI capability 是否可用。

### 6.2 顶部面板

顶部面板是当前项目改造重点之一。规范：

- TopPanel 是 CapabilityPackage，不归某个指挥官。
- 指挥官声明需要几个 caster、几个按钮、是否可降级。
- 地图声明是否占用顶部区域、过场是否隐藏指挥官 UI。
- PairPatch 只能修少数布局冲突，不得复制整套 UI。

## 7. Bank 与运行时状态规范

### 7.1 Bank 分区

Bank 必须分 owner：

| 类型 | owner | 访问规则 |
| --- | --- | --- |
| map-owned | 地图/战役 | Adapter 默认拒绝访问 |
| platform-owned | PlatformKernel | 只存平台状态和 probe |
| commander-owned | CommanderPackage | 只存指挥官自己的进度 |

Reborn 的 `cryswarmcoop`、`ZCampaign*`、`ZStory*`、`ZArmy`、`TCampaign` 等应按 map-owned 处理。

### 7.2 运行时状态寄存器

可以借鉴 Archipelago 的不可见控制器单位：

- 用隐藏、不可选、无敌 controller unit 承载运行时状态。
- 用 upgrade stack 或 unit property 表示可同步状态。
- 用周期性守护触发器修复 controller 丢失或被隐藏状态异常。

但这属于中长期能力，不应优先于 CompositionPlan 和 DataCenter 闭环。

## 8. 触发器与编辑器保存规范

### 8.1 触发器 ID 与中文乱码

经验规则：

- 变量名、函数名、脚本 ID 使用英文、数字和下划线。
- 显示名称可以中文，但内部 ID 不要中文。
- 如果使用中文编辑器且勾选“按名字获取/更换脚本 ID”，中文可能变成乱码，导致保存失败或脚本 ID 异常。
- 使用英文编辑器或 OB 翻译包可以降低问题，但翻译包可能把文本注入地图，需权衡。
- 触发器出现保存失败时，优先检查中文变量名、中文脚本 ID 和自动按名称改 ID 选项。

### 8.2 禁止把触发器修复当成普通文本替换

触发器相关改动必须：

- 先备份或在生成副本上做。
- 记录删除了哪些科技触发器或 hook。
- 用 galaxy-checker 和实际打开/保存验证。
- 遇到编辑器保存 bug 时，沉淀为经验文档和 checker 规则。

## 9. 本地化与路径规范

规则：

- 文件路径、目录名、内部 ID 尽量 ASCII。
- 中文只放本地化显示文本。
- zhCN 文本修改要走 localization scan。
- 不要用中文路径作为工具链输入输出路径。
- 第三方地图或 Mod 原路径有中文时，导入后在项目内建立 ASCII alias 或 manifest。

## 10. 验证规范

### 10.1 验证等级

| 等级 | 含义 | 不能声称 |
| --- | --- | --- |
| schema pass | 配置和 manifest 可解析 | 不能说明游戏能进 |
| static pass | toolkit / galaxy-checker 通过 | 不能说明运行时行为正确 |
| smoke pass | 能进图、无 ScriptError、进程正常 | 不能说明单位、科技、UI 正确 |
| unit diagnostics pass | 生产链、按钮、技能、Requirement、科技树有效 | 不能说明完整任务流程 |
| runtime probe pass | 游戏内探针确认运行时状态 | 仍需抽样任务行为 |
| full scenario pass | 任务目标、AI、胜负、Bank、UI、指挥官行为均验证 | 可作为组合完成证据 |

最终回复和文档必须明确验证等级，不得把 smoke pass 写成完整兼容。

### 10.2 单位诊断

遇到“兵营造不出兵”“造出来没技能”“科技升级对不上”“静态数据和运行时不同”时，必须按三层诊断：

1. 原始静态定义。
2. 依赖合并后的有效 Catalog。
3. 地图生命周期和 Galaxy runtime 执行后的运行时状态。

检查项：

- `CardLayouts`
- `Button AbilityCommand`
- `Requirement`
- `TechTreeUnitAllow`
- `TechTreeAbilityAllow`
- `UnitAbilityAdd/Remove`
- `CatalogFieldValueSet*`
- `Upgrade`
- `Behavior`
- 地图本地触发器科技 reset

### 10.3 运行时测试

改变地图、Mod、GameData、Galaxy、触发器、启动器或依赖顺序后，必须按对应入口进图验证。

纯文档、只读分析、独立工具设计文档可以免进图，但最终报告要明确“未改变运行时产物”。

## 11. 低成本任务下沉规范

低判断、高 token、高重复任务必须拆到本地任务包，交给便宜模型或脚本执行。

适合下沉：

- 依赖链批量盘点。
- 单位诊断矩阵初扫。
- Galaxy 错误清单聚合。
- Catalog trace 批量输出。
- 本地化名称反查。
- MPQ/组件目录结构清单。
- 验证日志与文档路径盘点。
- 全矩阵静态 CompositionPlan 生成与 diff。

不适合下沉：

- owner 决策。
- 是否接受 PairPatch。
- runtime ScriptError 根因判断。
- 指挥官与地图冲突的修复层选择。
- 架构边界调整。
- 提交和最终验证结论。

本地任务包位置：

```text
docs/低成本模型任务包/
docs/低成本模型任务输入/
docs/低成本模型产物/
```

每个任务包必须有：

- 输入文件。
- 输出目录。
- 期望格式。
- complete / incomplete 状态。
- needs-senior-review 标记。
- 不允许便宜模型直接修改项目源码。

## 12. 新增指挥官接入流程

1. 创建或登记 `Shared/Commanders/<Commander>.json`。
2. 创建 CommanderDataCenter 或登记现有 `CommanderUnits_*` 作为 pending。
3. 建立 `DataCenter.json`。
4. 拆分或登记数据空间：
   - Units
   - Buildings
   - Abilities
   - Buttons
   - Actors
   - Effects
   - Behaviors
   - Upgrades
   - Requirements
5. 登记 Galaxy runtime：
   - init
   - applyTech
   - createStartSquad
   - initUi
6. 补 expected producers / units / abilities / upgrades。
