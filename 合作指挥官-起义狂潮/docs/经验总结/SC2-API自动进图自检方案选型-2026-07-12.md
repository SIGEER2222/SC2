# SC2 API 自动进图自检方案选型

- 任务类型：架构选型 / 自检工作流设计
- 时间戳：2026-07-12
- 任务内容：阅读 `SC2-API-对接分析.md`，为“AI 自动进游戏获取兵种、建筑、科技、技能等运行时数据并用于自我检测”选择合适方案。
- 任务结果：选择 **Bank 文件诊断桥作为主方案，SC2API RequestObservation 作为辅助观测通道，python-sc2 只作为标准 AI 对战测试的旁路工具**。
- 任务耗时：约 20 分钟。
- 任务备注：本次是纯文档与架构选型，不修改地图、Mod、Galaxy、GameData 或启动器运行逻辑，因此不触发进图测试门禁。

## 一句话结论

当前项目要解决的核心不是“让 AI 玩标准天梯对战”，而是“让 AI 在合作指挥官、战役地图、7vs1、自定义依赖链里看到真实运行时数据”。因此不能把 python-sc2 作为主路线。

推荐建设一个项目内的 **RuntimeProbe Bridge**：

```text
地图 / Mod 触发器
  -> 写入 RuntimeProbe.SC2Bank
Python Probe Runner
  -> 监听 Bank
  -> 归一化 JSON
  -> 对比 DataCenter / CommanderPackage / CompositionPlan / 静态扫描结果
  -> 输出 VerificationReport
```

SC2API WebSocket 的 `RequestObservation` 可以并行作为外部观测通道，用于补充单位坐标、生命、订单、buff、可见性、升级列表等原始观测；但它不应替代 Bank，因为它看不到或不好解释很多项目真正关心的运行时语义，例如触发器注入、地图本地覆盖、战役阶段、命令卡可用性、Requirement 锁定原因和自定义诊断断言。

## 方案选择

### 主方案：Bank 文件诊断桥

适用范围：

- 合作指挥官 Mod。
- 7vs1 测试地图。
- 重生虫心 / 战役地图搬运。
- 指挥官和地图杂交后的运行时验证。
- 兵营造不出预期单位、单位缺技能、科技升级对不上、静态数据和运行时单位不一致等问题。

选择理由：

- 战役 / 自定义地图里，SC2API 直接控制能力有限，已有分析也说明 Neuro 项目最终把 Bank 作为实际主通道。
- Bank 数据由游戏内触发器写出，可以暴露项目真正需要的上下文，而不是只拿引擎原始观测。
- 可以把“运行时事实”写成稳定协议，供 AI、便宜模型、静态工具、报告系统复用。
- 可以和当前 Neuro 集成复用基础设施，而不是另起一套通信系统。
- 可用于无人值守自检：启动地图、等待 Bank 心跳、采样、断言、输出报告。

### 辅助方案：SC2API RequestObservation

适用范围：

- 确认地图里实际存在的单位、建筑、资源、订单、buff、生命、能量、建造进度、玩家升级列表。
- 做外部观测器或可视化。
- 作为 Bank 断言的旁证，发现触发器漏报或 Bank 协议错误。

限制：

- 对战役 / 自定义地图的动作控制不稳定，不能依赖它完成全部自动诊断。
- 原始单位 ID 需要映射回项目 Catalog / DataCenter / CommanderPackage 语义。
- 它更像“外部摄像头”，不是项目自检的业务协议。

### 不推荐主用：python-sc2 / burnysc2

适用范围：

- 标准 melee 类 AI vs AI。
- 以后如果把某些合作指挥官包装成标准对战模式，可以作为旁路测试。

不作为主方案的原因：

- 它要求 Python Bot 作为参与者进入游戏，更适合标准对战，不适合现有战役地图和复杂依赖链。
- 对地图触发器、战役阶段、地图本地覆盖、指挥官 Adapter、运行时注入等问题帮助有限。
- 当前痛点主要来自自定义数据空间和地图/Mod 继承关系，不是标准 Bot 操作问题。

## RuntimeProbe Bridge 设计

### 目标

让 AI 能自动完成以下闭环：

1. 启动指定地图 + 指挥官 + 依赖组合。
2. 进入游戏后由触发器写出运行时状态。
3. Python 监听 Bank 并生成结构化 JSON。
4. 工具链对比静态期望和运行时事实。
5. 输出可读、可复查、可回归的诊断报告。

### 诊断重点

优先覆盖当前最常见的问题：

- 生产链：兵营、工厂、星港、孵化场等是否能生产预期单位。
- 单位能力：造出来的兵是否带有预期技能、按钮、自动施法、行为。
- 科技升级：升级是否存在、是否能研究、研究后是否正确影响单位。
- 静态 / 运行时差异：XML 静态扫描说有，但进图后没有；或地图/依赖覆盖导致 ID 被替换。
- 地图适配：同一指挥官在不同战役地图里的单位、建筑、科技是否被父依赖覆盖。
- Neuro / AI 控制：AI 能否拿到足够状态并发出动作。

## Bank 协议草案

建议新建独立 Bank，例如：

```text
RuntimeProbe.SC2Bank
```

不要直接污染 Neuro 的业务 Bank。Neuro Bank 可以复用监听器、写入锁、watchdog、运行时状态判断，但诊断协议本身应独立，避免把“玩游戏动作协议”和“工程自检协议”耦合。

### probe_state

基础心跳与运行信息：

```text
run_id
composition_id
map_id
map_path
commander_id
player_id
game_time
phase
heartbeat
is_paused
is_in_mission
script_error_count
```

用途：

- 判断进图是否成功。
- 判断游戏是否还在运行。
- 关联一次启动、一次报告和一个组合配置。
- 记录 ScriptError 状态，避免误把“没有数据”当成“测试通过”。

### probe_units

单位与建筑摘要：

```text
player_id
unit_type_id
catalog_id
count
completed_count
in_progress_count
life_summary
energy_summary
owner
is_structure
is_worker
```

用途：

- 判断初始单位、建筑、刷怪、测试生产结果是否符合预期。
- 发现“造出来的不是目标单位”或“单位 ID 被父依赖覆盖”。

### probe_producers

生产建筑与可训练项：

```text
producer_unit_id
producer_catalog_id
producer_count
trainable_unit_ids
blocked_unit_ids
active_queue
last_order_ability
```

用途：

- 直接回答“兵营为什么造不出预期兵”。
- 区分缺按钮、Requirement 锁定、Ability 被覆盖、训练队列异常。

### probe_abilities

关键单位能力与命令卡：

```text
unit_type_id
ability_ids
command_card_button_ids
missing_expected_ability_ids
missing_expected_button_ids
autocast_flags
```

用途：

- 发现“造出来的兵没有技能”。
- 对比 DataCenter 中定义的 expected abilities。
- 对比静态 XML 与运行时实际可见按钮。

### probe_upgrades

科技与升级状态：

```text
upgrade_id
researched
available
in_progress
blocked_reason
affected_unit_ids
```

用途：

- 发现战役科技与指挥官科技对不上。
- 尤其适合鸡翅战役这类升级错位明显的地图。

### probe_assertions

游戏内断言结果：

```text
assertion_id
severity
status
expected
actual
message
source
```

用途：

- 触发器端直接输出判断结果。
- Python 端不需要理解所有 Galaxy 细节，也能得到明确失败点。

### probe_actions

外部请求触发器执行的诊断动作：

```text
action_id
action_name
target_player
target_unit_id
target_upgrade_id
args
```

建议动作：

- `spawn_unit`
- `select_producer`
- `try_train_unit`
- `try_research_upgrade`
- `dump_command_card`
- `dump_player_upgrades`
- `dump_unit_abilities`
- `advance_test_phase`

## Python Runner 设计

建议新增：

```text
合作指挥官-起义狂潮/scripts/runtime-probe/
  runtime_probe_runner.py
  bank_io.py
  normalize_probe.py
  compare_expected.py
  schemas/
    runtime-probe.schema.json
```

职责：

- 监听 `RuntimeProbe.SC2Bank`。
- 解析 Bank XML。
- 将 Bank 数据转换为 JSON。
- 读取 `DataCenter.json`、`CompositionPlan`、CommanderPackage 定义和静态扫描结果。
- 输出诊断报告。

输出路径建议：

```text
合作指挥官-起义狂潮/out/runtime-probes/<composition_id>/<run_id>.json
合作指挥官-起义狂潮/out/runtime-probes/<composition_id>/<run_id>.md
```

报告必须区分：

- `launch_pass`：进程启动成功。
- `map_loaded`：Bank 心跳出现。
- `probe_complete`：诊断阶段完成。
- `static_match`：静态期望与运行时事实匹配。
- `runtime_assertions_pass`：触发器断言通过。
- `script_error_free`：未发现 ScriptError。

## 启动器集成

第一阶段不要重做启动器，建议在现有 Neuro / 7vs1 启动链旁边加 probe 模式。

建议新增：

```text
合作指挥官-起义狂潮/scripts/runtime-probe/launch-runtime-probe.ps1
```

但实现时应遵守项目文件操作约束，不用临时 `$scriptPath` + `Out-File` 写脚本。

参数草案：

```text
-MapPath
-CommanderId
-CompositionId
-ProbeMode NoActionProbe|ProductionProbe|TechProbe|AbilityProbe|FullProbe
-TimeoutSeconds
-OutputDir
-UseSc2ApiObservation
```

初期只做 `NoActionProbe`：

1. 启动地图。
2. 等待 Bank 心跳。
3. 读取已有单位、建筑、升级、阶段信息。
4. 生成报告。
5. 不主动执行训练或升级动作。

第二阶段再做 `ProductionProbe` 和 `AbilityProbe`。

## 与数据中心的关系

RuntimeProbe 不应该自己维护一套“正确答案”。正确答案应来自数据中心。

建议数据来源优先级：

1. `DataCenter.json`：组合、依赖、包、Adapter、预期能力。
2. CommanderPackage：指挥官规范定义。
3. CompositionPlan：某次地图 + 指挥官组合的有效计划。
4. 静态扫描：Catalog trace / diagnose-unit / effective dependency 结果。
5. RuntimeProbe：进图后的事实。

自检逻辑应输出“三段式差异”：

```text
Expected from DataCenter
Static effective Catalog
Runtime observed fact
```

这样才能判断问题位于：

- 数据中心期望错了。
- 依赖链选错了。
- Catalog 被父级或地图覆盖了。
- Galaxy 运行时改掉了。
- 触发器诊断漏报。

## 与 Neuro 的关系

Neuro 集成适合复用，但不建议完全绑定。

推荐关系：

```text
NeuroBridge
  负责 LLM 玩游戏和动作协议

RuntimeProbeBridge
  负责工程自检和诊断协议

Shared Bank Runtime
  复用 Bank 监听、原子写入、心跳、进程监控、超时、报告
```

这样未来可以做到：

- 没有 Neuro 时也能跑自检。
- 有 Neuro 时，AI 可以读取 RuntimeProbe 报告后决定下一步。
- 便宜模型可以只处理 RuntimeProbe JSON，不必理解整套地图工程。

## 分阶段落地计划

### Phase 0：协议定稿

产物：

- `docs/技术设计/RuntimeProbe-Bank协议.md`
- `scripts/runtime-probe/schemas/runtime-probe.schema.json`

验收：

- Bank section 和 JSON schema 能表达单位、建筑、科技、技能、断言、心跳。
- 能覆盖 Raynor Marine / Marauder / Vulture 一类最小诊断案例。

### Phase 1：只读 RuntimeProbe

产物：

- `RuntimeProbe.SC2Mod` 或挂在现有测试 Mod 下的 RuntimeProbe library。
- Python Bank watcher。
- `NoActionProbe` 报告。

验收：

- 启动 7vs1 测试地图后能拿到心跳、玩家、初始单位、建筑、已研究升级。
- 输出 JSON 和 Markdown 报告。
- 不要求 AI 操作单位。

### Phase 2：生产链探针

产物：

- `try_train_unit` probe action。
- producer dump。
- trainable / blocked / queue 状态报告。

验收：

- 能对兵营、工厂、星港等生产建筑输出可生产项。
- 能发现“期望可造但运行时不可造”的单位。
- 能把失败分类到缺 Ability、缺 Button、Requirement 锁定或依赖覆盖。

### Phase 3：技能与科技探针

产物：

- `dump_unit_abilities`
- `dump_command_card`
- `try_research_upgrade`
- upgrade availability dump。

验收：

- 能发现单位缺技能、按钮不显示、自动施法状态错误。
- 能发现科技升级对不上，尤其是战役图与指挥官 Mod 混合时的覆盖问题。

### Phase 4：SC2API 辅助观测

产物：

- 可选 `RequestObservation` 采集器。
- unit_type_id / ability_id / upgrade_id 映射表。
- Bank 报告和 SC2API 原始观测交叉校验。

验收：

- 能确认 Bank 中的单位数量和 SC2API 观测数量是否一致。
- 能发现触发器漏报。
- 不把 SC2API 作为唯一判定来源。

### Phase 5：自动回归矩阵

产物：

- 组合矩阵：
  - commander x map
  - commander x reborn campaign map
  - commander x 7vs1 test map
- `VerificationReport` 汇总。
- 失败用例自动生成低成本模型任务包。

验收：

- 能批量找出哪些地图缺 RuntimeProbe 支持。
- 能按失败类型输出待修复清单。
- 能把高 token 的重复扫描任务拆给便宜模型。

## 风险与处理

### Bank IO 延迟和竞争

处理：

- 复用 Neuro 的原子写入、锁、watchdog、合成事件机制。
- 所有 probe action 带 `action_id`，避免重复执行。
- Bank 心跳必须单调变化。

### 触发器写入能力有限

处理：

- 第一阶段只写最容易取得的数据。
- 难取的数据用“动作式探针”获取，例如选择单位后 dump command card。
- 无法稳定获取的字段标为 `unknown`，不能静默当成通过。

### 地图和依赖覆盖

处理：

- 每份报告必须记录有效依赖链。
- 报告必须区分父级 Mod、指挥官 Mod、Adapter、地图本地覆盖。
- 如果 RuntimeProbe 所在依赖没有被实际加载，报告必须失败而不是空通过。

### ScriptError 和保存 bug

处理：

- RuntimeProbe 内部 ID、变量名、函数名保持 ASCII。
- 不依赖中文变量名生成脚本 ID。
- 改 Galaxy 前先跑 checker，checker 漏报则补规则和回归。

## 最终建议

采用如下主线：

```text
RuntimeProbe Bank Bridge
  作为自检主协议

SC2API RequestObservation
  作为可选外部观测器

python-sc2
  仅作为标准 AI 对战或未来 melee-like 适配测试
```

这个选择最贴合当前工程问题：依赖项是地图的父级，地图会继承和覆盖父级数据；静态 XML 正确不代表运行时正确；自定义对战能用也不代表战役里能用。Bank 诊断桥可以把这些运行时事实从游戏内显式写出来，是后续实现“任意指挥官到任意地图玩”的必要自检层。

### 仍未解决的问题

1. `MapScript.galaxy` 的 `include "LibC0F50AA6"` 仍会间歇性复现：
   - 有的运行能过 `Alerts.txt`；
   - 有的运行仍会在稍后生成 `ScriptError.txt` 和 crash 包。
2. 方案 A 的 websocket 链路仍不稳定：
   - `/sc2api` 握手可以成功；
   - 第一发 protobuf `RequestPing` 后收到的是 `WSMsgType.CLOSED`，不是正常二进制响应；
   - 后续连接常变成 `Server disconnected`。
3. `wait-for-game-ready.ps1` 仍存在误判窗口：
   - 并发终端或启动早期轮询时，可能把“仍在启动中”误判成失败；
   - 需要把它和真正的 crash / ScriptError 证据进一步对齐。

### 已排除但不成立的修法

1. 直接从 `ttosh02_7vs1.SC2Map/MapScript.galaxy` 删除 `LibC0F50AA6`、`LibDF8E6945`、`Lib0940FFB7`、`Lib975E2FE9` 这 4 个静态引用：
   - 实测会让**不带 API 的普通启动也直接失败**；
   - 因此该修法已回退，不是正确方向。
2. 仅把这些库对应的 owner mod 挂到 `CoreRuntime` 扩展边界：
   - 能改变 live `DocumentHeader`；
   - 但端到端仍未消除 `LibC0F50AA6` 与 API 断连问题。

### 当前判断

当前最像是一个“**live 安装内容存在，但游戏最终用于解析 `MapScript` 的依赖边界仍未完全对齐**”的问题。也就是说：

- 磁盘上的文件和一部分 header 依赖已经是对的；
- 但 SC2 编译 / 启动期真正采用的边界，和当前脚本假设的边界还不是同一套。

这也是为什么会出现下面这种矛盾现象：

- `galaxy-checker` 能看到 `LibC0F50AA6.galaxy`；
- live map / live mod 上也确实存在该文件；
- 但运行时仍可能报 `include "LibC0F50AA6"` 缺失。

### 下一步

1. 继续追 `Set-PackageDependencies` 写入后的 **live map `DocumentHeader` 实际依赖集合**，不要再只看 `DocumentInfo` 文本。
