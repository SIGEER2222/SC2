# 按指挥官过滤生成单位到测试地图

**日期**: 2026-07-05
**任务**: 在阿巴瑟之心测试地图中支持 `-Commander` 参数，只生成指定指挥官的单位到地图中央

## 背景

测试地图 `AbathurHeartTest_unpacked` 默认会把 25 个指挥官组、663 个单位全部生成到地图上，单位过多不便逐个查看。需要支持按指挥官 ID 过滤，单独生成某个指挥官的单位到地图中央。

## 实现方案

### 全局变量 + 启动脚本正则替换（不动源文件）

**MapScript.galaxy 端**：
```galaxy
string gv_commanderFilter = "";

bool gf_CommanderMatchesFilter (string identifier, string filter) {
    if (filter == "") { return true; }
    if (StringFind(identifier, filter, false) > 0) { return true; }
    return false;
}
```

**test-abathur-heart.ps1 端**：
```powershell
function Set-CommanderFilter {
    param([string]$MapScriptPath, [string]$Commander)
    $content = [System.IO.File]::ReadAllText($MapScriptPath)
    $pattern = 'gv_commanderFilter\s*=\s*"[^"]*"\s*;'
    $replacement = 'gv_commanderFilter = "' + $Commander + '";'
    $newContent = [regex]::Replace($content, $pattern, $replacement)
    [System.IO.File]::WriteAllText($MapScriptPath, $newContent, [System.Text.UTF8Encoding]::new($false))
}

# 在同步地图后调用，只改 mapLive 下的副本，不动源文件
if ($Commander -ne "") {
    Set-CommanderFilter -MapScriptPath (Join-Path $mapLive "MapScript.galaxy") -Commander $Commander
}
```

## 关键坑

### 坑 1: `StringCase` 在 mod 环境下编译报错

**现象**：调用 `StringCase(filter, true)` 报错：
```
Script compile error: MapScript.galaxy (80), 参数类型同函数定义不匹配
```

**原因**：虽然 `natives.galaxy` 中 `StringCase` 签名是 `(string s, bool upper)`，但 VioletsHoTSReworkMod 等 mod 替换了 NativeLib，导致该函数不可用或签名改变。

**修复**：改用 `StringFind(identifier, filter, false)`（第三个参数 `false` = 不区分大小写），返回值 > 0 即包含匹配。一行代码搞定，更简洁。

### 坑 2: PowerShell heredoc 不支持

**现象**：`git commit -m "$(cat <<'EOF' ... EOF)"` 在 PowerShell 中报错：
```
Missing file specification after redirection operator.
```

**修复**：用 PowerShell here-string `@'...'@` 或 `@"..."@`，再传给 `-m` 参数：
```powershell
$msg = @'
commit 说明第一行
commit 说明第二行
'@
git commit -m $msg
```

### 坑 3: trae-add.ps1 包装脚本不存在

**现象**：AGENTS.md 列出了 `scripts/trae-add.ps1` 包装脚本，但实际仓库中不存在该文件。

**修复**：直接用 `git add "具体文件路径"`，明确指定文件，符合 AGENTS.md「禁止使用 `git add .` / `git add -A`」的要求。

## 布局策略

- **无过滤**（生成全部 25 组）：从左上角 (4, 124) 开始，5 列 × N 行铺开
- **有过滤**（匹配 1 组或几组）：从地图中央偏上 (30, 110) 开始，方便查看
- 过滤后重新排列位置，不留空位（即匹配的第 2 个组不会被错位到第 N 列）

## 用法示例

```powershell
# 只生成阿巴瑟（34 个单位）
.\test-abathur-heart.ps1 -Commander "Cmdr_Abathur"

# 只生成 Violets 的凯瑞甘子组
.\test-abathur-heart.ps1 -Commander "Violets_Kerrigan"

# 前缀匹配，生成所有 Violets 子组（10 个组）
.\test-abathur-heart.ps1 -Commander "Violets_"

# 不指定 = 生成全部 25 个组（原行为）
.\test-abathur-heart.ps1
```

## 附录：如何查找指定指挥官的全部单位和建筑

### 一、底层原理：扫描 + 分组（静态枚举，非动态遍历）

查找逻辑由 [_gen_abathur_heart_catalog.py](file:///E:/Code/MyMod/SC2/合作指挥官-起义狂潮/scripts/_gen_abathur_heart_catalog.py) 实现，分两种来源：

#### 1. 单指挥官 mod（1 个 mod = 1 个指挥官组）

读取 mod 里的 `Base.SC2Data/GameData/UnitData.xml`，提取所有 `<CUnit id="XXX">` 标签。

- **MPQ 格式 mod**（如 `Ihanrii.SC2Mod`）：用 `mpyq` 解包读取
- **目录格式 mod**（如 `VioletsHoTSReworkMod.SC2Mod`）：直接读文件

配置在 `SINGLE_COMMANDER_MODS` 列表中：
```python
SINGLE_COMMANDER_MODS = [
    ("CM_Core_Zhelus.SC2Mod",   "Cmdr_Dehaka",  "Dehaka（迪哈卡）"),
    ("Alenger\\6阿巴瑟.SC2Mod", "Cmdr_Abathur", "Abathur（阿巴瑟）"),
    ...
]
```

#### 2. 共享库 mod（1 个 mod 内多个子指挥官）

`VioletsHoTSReworkMod.SC2Mod` 里包含 10 个子指挥官，通过 `classify_violets_unit()` 按单位 ID 关键字分组：
```python
def classify_violets_unit(unit_id: str) -> str:
    if unit_id.startswith("Mengsk"):  return "Violets_Mengsk"
    if unit_id.startswith("Dehaka"):  return "Violets_Dehaka"
    if unit_id.endswith("Aiur"):      return "Violets_Artanis"
    if unit_id.endswith("Shakuras"):  return "Violets_Zeratul"
    ...
    return "Violets_Shared"  # 无法分类的进共享组
```

#### 3. 过滤规则（避免把基础种族单位也列出来）

在 `extract_units_from_xml()` 中过滤掉：
- **基础种族单位**（`BASE_RACE_UNITS` 集合，如 `Marine`/`Zealot`/`Drone` 等 100+ 个）
- **状态变体**（以 `Burrowed`/`Cocoon`/`Uprooted`/`Flying` 结尾）
- **武器/投射物**（parent 含 `MISSILE`，或 ID 含 `MISSILE`/`WEAPON`/`PROJECTILE`）

#### 4. 输出

扫描结果固化到 [LibAbathurHeartCatalog.galaxy](file:///E:/Code/MyMod/SC2/合作指挥官-起义狂潮/Maps/AbathurHeartTest_unpacked/Base.SC2Data/LibAbathurHeartCatalog.galaxy)（运行时数据表）：
```galaxy
const int gv_c_AH_ModCount = 25;       // 25 个指挥官组
const int gv_c_AH_TotalUnits = 663;    // 共 663 个单位
string[25] gv_AH_ModIdentifiers;       // 指挥官 ID（Cmdr_Abathur 等）
string[25] gv_AH_ModLabels;            // 显示标签（"Abathur（阿巴瑟）"）
int[25] gv_AH_UnitOffsets;             // 每组在 Units 数组的起始偏移
int[25] gv_AH_UnitCounts;              // 每组的单位数
string[663] gv_AH_Units;               // 所有单位的 ID 平铺数组
```

**重要：这是静态枚举，不是动态遍历。** 单位列表在生成器运行时一次性写入 galaxy 库，游戏运行时只查表。mod 更新后需要重新运行 `_gen_abathur_heart_catalog.py`。

### 二、查询指定指挥官的 3 种方法

#### 方法 A：查扫描报告（最快，不用启动游戏）

直接读 [docs/阿巴瑟之心mod扫描报告.md](file:///E:/Code/MyMod/SC2/合作指挥官-起义狂潮/docs/阿巴瑟之心mod扫描报告.md)，已列出 25 个指挥官的全部单位清单。

例如查阿巴瑟：
```

- 指挥官 ID: `Cmdr_Abathur`
- 来源: `Alenger\6阿巴瑟.SC2Mod`
- 6baowenchaoxue, 6baozipachong, 6buyuchonghou, 6chongluan, ...
```

#### 方法 B：用 sc2_unit_explorer.py 查单个单位的生产链（动态分析）

```powershell

python scripts/sc2_unit_explorer.py Drone --depth 2
```

这是 AGENTS.md 推荐的工具，但只支持查单个单位，不支持按指挥官批量查询。

#### 方法 C：进游戏实地查看（最直观）

```powershell
# 只生成阿巴瑟的 34 个单位到地图中央
.\scripts\test-abathur-heart.ps1 -Commander "Cmdr_Abathur"

# 只生成 Violets 凯瑞甘子组
.\scripts\test-abathur-heart.ps1 -Commander "Violets_Kerrigan"

# 前缀匹配，生成所有 Violets 子组
.\scripts\test-abathur-heart.ps1 -Commander "Violets_"
```

启动后地图中央会出现该指挥官的全部单位和建筑，可手动查看。

### 三、当前方案的局限

| 局限 | 说明 |
|------|------|
| **静态枚举** | 单位列表是生成器一次性扫描的，mod 更新后需要重新运行 `_gen_abathur_heart_catalog.py` |
| **不区分单位和建筑** | 当前把 `<CUnit>` 都当成"单位"，没有按 `FlagArray` 或 `Building` 字段区分建筑/单位/英雄 |
| **Violets_Shared 有 50 个未分类** | `VioletsHoTSReworkMod` 里没有明显 ID 前缀的单位进了 Shared 组，可能漏分 |
| **不解析生产链** | 只列出 mod 里定义的单位，不展开"工蜂能变异成什么""兵营能造什么"这种动态关系 |

### 四、若要更精确地查（未来增强方向）

#### 1. 区分单位和建筑

修改 `_gen_abathur_heart_catalog.py` 的 `extract_units_from_xml()`，解析 `<CUnit>` 的 `FlagArray` 字段：
```xml
<CUnit id="XXX" parent="...">
  <FlagArray index="Building" value="1"/>  <!-- 建筑 -->
  <FlagArray index="Hero" value="1"/>      <!-- 英雄 -->
</CUnit>
```

#### 2. 按生产链动态提取（更准确）

参考 AGENTS.md 里 `sc2_unit_explorer.py` 的能力，从一个指挥官的起始英雄出发，递归展开：
- 工蜂 → CAbilBuild → 可建造建筑
- 幼虫 → CAbilTrain → 可变异单位
- 建筑 → CAbilTrain/CAbilResearch → 可生产单位/科技

但这需要运行时数据合并，复杂度比静态枚举高得多。
